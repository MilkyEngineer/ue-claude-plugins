# UnrealAgentKit: design

UnrealAgentKit is a Claude Code plugin with two parts:
- a multi-agent workflow for Unreal Engine projects: tiered workers, a runner that cannot edit, a read-only researcher and read-only reviewers, epic briefs, and delegation;
- the tools that workflow needs, gathered in one CLI, `uak`:
  - a queued lock around editor and build runs;
  - detached runs that are tracked, and a wait for one to end;
  - a single-file compile check;
  - build and test wrappers;
  - a version-control abstraction, with Perforce writes up to shelving;
  - Horde preflights and a quiet wait for their results.

It must not depend on any particular engine, project, platform or version-control system. Apart from Claude Code, it uses only what building Unreal Engine already requires: the engine's bundled .NET SDK, and the prebuilt C# libraries the engine ships (`EpicGames.*` and the third-party libraries beside them). `uak` itself needs no NuGet package. NuGet is needed only for the tests (MSTest.Sdk) and for a self-contained publish (the .NET runtime pack, which the bundled SDK lacks).

The owner decided on 2026-10-01:
- the name is UnrealAgentKit, living in the `ue-claude-plugins` marketplace;
- UE 5.8 and 5.7, installed or built from source (a source build has no `Engine/Build/InstalledBuild.txt`; tested with a 5.6 source build, whose projects may sit inside the engine's root folder);
- Windows now, but keep everything platform-neutral (no Windows-only code without a Linux/Mac path or a clear TODO).

## Layout

```
plugins/unreal-agent-kit/
  .claude-plugin/plugin.json
  agents/            tiered workers, the runner, the researcher and the reviewers (generic ground rules)
  skills/            the workflow skill (briefs, delegation, resume or respawn, reviews, doc sync) and templates
  hooks/             SessionStart: says when this version's uak isn't published yet
  bin/               uak and uak.cmd: run this version's published uak, so uak is on PATH in Claude Code sessions
  docs/              install, settings, CLAUDE.md snippet
  tools/
    UnrealAgentKit.sln, Directory.Build.props, global.json, build/EpicGames.props
    src/AgentKit.Core      context resolution, process running, JSON, logging, IUakCommand
    src/AgentKit.Locking   the queued lock
    src/AgentKit.Runs      detached runs and their registry
    src/AgentKit.Vcs       IVersionControl: Git, Perforce, None; Perforce writes (edit, add, reopen, change, shelve)
    src/AgentKit.Horde     uak horde: the Horde server setting, sign-in, streams, preflights and jobs
    src/AgentKit.Unreal    compile (UBT -SingleFile), build, automation tests
    src/uak                the CLI host
    src/EpicGames.Perforce.FromSource  the engine's EpicGames.Perforce source, built when no prebuilt DLL exists
    tests/AgentKit.*.Tests MSTest (MSTest.Sdk), one project per library
```

## Build

`<Engine>/Binaries/ThirdParty/DotNet/<version>/<platform>/dotnet build tools/UnrealAgentKit.sln`, using the engine's bundled SDK.

- **Target framework:** the engine's own, read from the `tfm` in its `UnrealBuildTool.runtimeconfig.json` (`UakEngineTargetFramework`), so the engine's libraries always load. UE 5.8 bundles SDK 10.0.203 (`net10.0`); UE 5.7 bundles 8.0.412 (`net8.0`, C# 12). When that file can't be read, the running SDK's own major version (`UakSdkTargetFramework`, from the `sdk/<version>` folder name in `MSBuildBinPath`), which that SDK can always build; `net10.0` only when neither is known.
- **Newer .NET APIs** stay out of the code, or behind `#if NET9_0_OR_GREATER` with a .NET 8 path (`UakJson`'s tab indentation is the one case). Differences between engine versions' libraries are keyed on what the engine ships, not on its version: `UAK_PERFORCE_TRACER` is defined when OpenTelemetry.Api sits beside EpicGames.Perforce (UE 5.8's `IPerforceConnection` has a `Tracer`; 5.7's has none).
- Output goes under `tools/bin` and `tools/obj`. Never write into an engine directory: installed engines sit under Program Files. (The bundled SDK may update its own metadata folder under the engine's DotNet directory; the kit's build writes nothing else there.)
- Tests: from `tools/`, `dotnet test --solution UnrealAgentKit.sln` with SDK 10 (Microsoft.Testing.Platform, set in `tools/global.json`, which is only found from `tools/`), or `dotnet test UnrealAgentKit.sln` with SDK 8 (VSTest; the test projects support both).
- Set `DOTNET_CLI_TELEMETRY_OPTOUT=1`, `DOTNET_NOLOGO=1` and `DOTNET_GENERATE_ASPNET_CERTIFICATE=false` for kit builds.
- Warnings are errors.

### Installing `uak` (lead's decision, 2026-10-01)

- **How:** a self-contained publish of `tools/src/uak` for the host's runtime identifier, so it runs with no system-wide dotnet.
- **Where:** `$UAK_HOME` (default `~/.unreal-agent-kit`) plus `/<kit version>/`. That is outside the plugin folder, because Claude Code replaces plugin folders on update, and versioned, so an update never overwrites a running binary.
- **Fallback:** if self-contained doesn't work cleanly, `<engine dotnet> uak.dll`.
- **Which engine:** the publish builds against the engine `build/EpicGames.props` finds, so a `UAK_ENGINE` set in the environment (or in a project's `.claude/settings.local.json`, which Claude Code passes to every command) chooses the engine of the next publish too, even when another engine's `dotnet` runs it. The docs say so.
- **NuGet:** the bundled SDKs carry no .NET runtime pack, so the first self-contained publish downloads one (Microsoft.NETCore.App.Runtime.<rid>). `-p:SelfContained=false` needs nothing from NuGet, but then `uak` runs on the engine's dotnet (`DOTNET_ROOT`).
- **Project commands:** the host also loads `IUakCommand` assemblies from the folders in `UAK_COMMAND_PATHS`, and from `<Project>/.uak/commands/` only when `UAK_PROJECT_COMMANDS=1` (or `true`) or that folder is listed in `UAK_COMMAND_PATHS` (a cloned repository's code never runs by default). Folders outside the kit load lazily: only for a command the kit lacks, or for `uak help -all`. Entries in `UAK_COMMAND_PATHS` must be absolute; a relative entry is skipped with a warning, because it would depend on the current folder. That way a project adds its own tools without changing the kit. A command assembly must target a framework no newer than `uak`'s, which is the engine's that `uak` was published with (`net8.0` loads on both UE 5.7 and 5.8 builds); `uak env`'s `uak:` line shows `uak`'s framework, the runtime it runs on, and the engine version it was built against (`UakEngineVersion`, embedded at build time as assembly metadata by `build/EpicGames.props`).

## Engine libraries

`build/EpicGames.props` is owned by Core.
- **Engine directory.** It finds the engine from the `UakEngineDir` property, else from the `UAK_ENGINE` environment variable, else from the engine whose bundled dotnet runs the build. It resolves `UakEngineRoot` (the root, with a trailing slash) and `UakEpicGamesDir`: `<root>Engine/Binaries/DotNET/UnrealBuildTool/`, or `AutomationTool/` beside it when `UnrealBuildTool/` has no `EpicGames.Build.dll`. It also reads `UakEngineVersion` (Major.Minor.Patch) from the engine's `Build.version`.
- **References.** It references the prebuilt `EpicGames.Core`, `.Build`, `.IoHash` and `.MsBuild` that the engine ships in `.../UnrealBuildTool`, and their run-time dependency closure from the same folder (Microsoft.Extensions.*, Polly, Blake3 and its native library, and the rest, as `UnrealBuildTool.deps.json` lists them). All are file references with `Private=true`, so they are copied next to `uak`. No NuGet package is involved, and the versions always match the engine.
- **EpicGames.Perforce.** The engine ships it prebuilt with AutomationTool: in `AutomationUtils/<tfm>/` in UE 5.8, and directly in `AutomationUtils/` in UE 5.7. AgentKit.Vcs references that DLL itself, based on `$(UakEngineRoot)`: the resolved engine root, with a trailing slash. `UakEngineDir` is only the optional input. It is not in `build/EpicGames.props`, because only AgentKit.Vcs and its tests need it.
  - Its one third-party dependency comes from the engine too: OpenTelemetry.Api beside it (5.8), or System.Linq.Async in `AutomationTool/` (5.7). No NuGet package.
  - We use our own `P4ProcessConnection`, an `IPerforceConnection` that runs `p4 -G` (found on PATH only) with a per-command timeout (`UAK_P4_TIMEOUT`, 15 s by default), so no native library is needed.
  - `src/AgentKit.Vcs/EpicGames.Perforce.props` holds the reference. It prefers `AutomationUtils/$(TargetFramework)/`, then `AutomationUtils/`, and `-p:UakPerforceDll=<path>` overrides both.
  - **Source builds** have no AutomationTool until someone builds it, so there is no prebuilt DLL. Then `src/EpicGames.Perforce.FromSource` compiles the engine's own `Engine/Source/Programs/Shared/EpicGames.Perforce` source (assembly name `EpicGames.Perforce`, versioned with `UakEngineVersion`) into the kit's `tools/bin`, against the engine's prebuilt EpicGames.Core. Nothing is written into the engine. The kit's warning and analyzer rules don't apply to that code.
    - Its third-party dependency (System.Linq.Async up to UE 5.7, OpenTelemetry.Api in 5.8) is looked for, by `src/EpicGames.Perforce.FromSource/Dependencies.props`, in the engine's `UnrealBuildTool/`, then `AutomationTool/`, then `AutomationTool/AutomationUtils/` and `AutomationUtils/<tfm>/`. A 5.7 or older source build has System.Linq.Async in `UnrealBuildTool/`. A 5.8 source build has no OpenTelemetry.Api until AutomationTool is built: when the engine's `IPerforceConnection.cs` uses OpenTelemetry and no `OpenTelemetry.Api.dll` exists in those folders, the build fails at once, telling the user to run `Engine/Build/BatchFiles/BuildUAT.bat` (`BuildUAT.sh` on Linux and Mac) once.
    - It is not in the solution, so `Directory.Build.props` sets `ShouldUnsetParentConfigurationAndPlatform=false` (and the reference passes `SetConfiguration`): a Release build builds it as Release.
  - The build fails with a clear message if there is neither a DLL nor the source.
  - We don't use `PerforceConnection` itself: it starts a bare `p4.exe` (which Windows looks up in the current directory first) and has no time limit.
  - The API we use, the same in 5.7 and 5.8: `PerforceSettings(IPerforceEnvironment)`, `IPerforceConnection`, `IPerforceOutput`, `PerforceRecord.FromFields`, `TryGetInfoAsync`, `TryGetChangesAsync`, `TryFStatAsync`, `TryAddAsync`, `AddOptions.IncludeWildcards` and `InfoOptions`.
- **EpicGames.Horde.** UnrealBuildTool references it, so every engine with a built UnrealBuildTool ships it prebuilt in `Engine/Binaries/DotNET/UnrealBuildTool/`, with its dependency closure (EpicGames.OIDC, Grpc, IdentityModel and the rest, as `UnrealBuildTool.deps.json` lists them). `src/AgentKit.Horde/EpicGames.Horde.props` references that DLL and closure from the same folder, imported by AgentKit.Horde and its tests only; each reference is conditional on its file, and a missing `EpicGames.Horde.dll` fails the build. It is not built from source (that needs Grpc.Tools code generation and a dozen NuGet packages). uak uses its HTTP client, its OIDC sign-in and token cache, and its request types; not its storage or compute code, so the storage code's native libraries (Oodle, e_sqlite3) are not copied.
- **Use what exists.** Where an EpicGames library already does the job, use it. Examples:
  - `EpicGames.Core`: `SingleInstanceMutex`, `ManagedProcess`, `FileReference` and `DirectoryReference`, `CommandLineArguments`, JSON helpers;
  - `EpicGames.Build`: `GlobalSingleInstanceMutex.GetUniqueMutexForPath`;
  - `EpicGames.Perforce`: its `-G` record parsing and settings, behind our `P4ProcessConnection`.
- **Version skew.** Keep the surface we use small, and build and test with every supported engine's own SDK. `ManagedProcess.Kill` is one example: 5.8 has it and 5.7 doesn't, so `ProcessRunner` disposes the process instead, which terminates it the same way.

## Command line

`uak [-project=<path>] [-engine=<path>] <command...> [arguments]`, in UE style (`-Key=Value`, case-insensitive). `uak help [command]` gives help.

Global options (`-project=`, `-engine=`, `-vcs=`, `-verbose`, `-help`) are parsed only before the command path. Everything after the command path reaches `RunAsync` verbatim, including a literal `--` and all that follows it. `uak <command> -help` shows that command's help. A partial path (`uak lock`) lists its subcommands and exits 2.

- **Commands** implement `AgentKit.Core.IUakCommand`, and parse their own arguments with `UakArguments`. The host (`UakHost`, in Core) finds implementations by reflection, so adding a command never edits the host. It searches:
  - every AgentKit.*.dll next to `uak`;
  - the folders in `UAK_COMMAND_PATHS`;
  - `<Project>/.uak/commands/`, only when opted in (see "Installing `uak`"), and lazily.

  Only assemblies that reference AgentKit.Core are loaded. A duplicate name is a warning.
- **`uak env` sections** come from the `IUakEnvReporter` implementations in the kit's own assemblies. Kit commands, `uak env`, `uak help` and `uak help <kit command>` never load other folders (`uak help <a name the kit lacks>` and `uak help -all` load the opted-in ones); when the project folder exists but isn't opted in, `help` and `env` say so in one line on stderr.
- **Exit codes:** 0 for success, 1 for failure (including a cancel), and 2 for a usage or setup error. Some commands add their own: `uak runs wait` uses 3 when its `-timeout` passed while the run still runs, `uak test` 3 when only unexpected tests stand between it and a pass, `uak mutate` 3 to 6 (see "Unreal operations"), and the `uak horde` commands use 3 to 7 (see "Horde"). The first Ctrl+C cancels the command; a second one kills `uak`.
- **`UAK_HOME`** (default `~/.unreal-agent-kit`) holds both the versioned installs and the fallback `State/` folder.
- **Version:** `Directory.Build.props`'s `<Version>` must equal `.claude-plugin/plugin.json`'s version.
- **Release rule:** every change that reaches users (anything under the plugin folder that an installed copy would see: agents, skills, hooks, docs or `uak` itself) bumps the version, in both files, in the same commit. Claude Code delivers a plugin update only when the version changes, and the SessionStart hook prompts a republish of `uak` only for a version that has no install yet.

## Resolving the engine and project

Core's `UakContextResolver` builds a `UakContext`.

The project comes from:
1. `-project=`;
2. the `UAK_PROJECT` environment variable;
3. otherwise, the nearest `*.uproject` found by walking up from the current directory. A directory holding more than one `.uproject` is an error that names them.

The engine comes from:
1. `-engine=`;
2. the `UAK_ENGINE` environment variable;
3. otherwise, the `.uproject`'s `EngineAssociation`, read as Unreal reads it (UE 5.8, `FDesktopPlatformBase::GetEngineIdentifierForProject` in `Engine/Source/Developer/DesktopPlatform/Private/DesktopPlatformBase.cpp`):
   - A non-empty value decides. A value holding `/` or `\` is a path, relative to the project's folder. Any other value is an identifier, looked up:
     - on Windows, in `HKCU\Software\Epic Games\Unreal Engine\Builds`, then in the launcher's installs (`HKLM\SOFTWARE\EpicGames\Unreal Engine\<version>` InstalledDirectory, then `LauncherInstalled.dat`);
     - on Linux and Mac, in UE's application settings folder (`~/.config/Epic` on Linux, `~/Library/Application Support/Epic` on Mac): `UnrealEngine/Install.ini` [Installations], then `UnrealEngineLauncher/LauncherInstalled.dat`.
   - A non-empty value that names no engine is an error, as in Unreal: `uak` never falls back to an engine that happens to contain the project.
   - An empty value means the engine root that contains the project (a source build with the project inside it). As in Unreal, the search starts at the project folder's parent and walks up.

   GUIDs match with or without braces. Unreal recognises an engine root by its `Engine/Binaries` and `Engine/Build` folders; `uak` needs `Engine/Build/Build.version` (below). The HKLM key is a `uak` addition: the launcher writes it for the same installs as `LauncherInstalled.dat`. `-project=` also accepts a directory that holds exactly one `.uproject`.

The engine root is the directory that contains `Engine/Build/Build.version`. Paths may be given as the root or as its `Engine` folder.

- **State directory:** `<Project>/Saved/AgentKit`, else `<EngineRoot>/Engine/Saved/AgentKit/Projects/<project key>` if that is writable, else `$UAK_HOME/State/<project key>`, where `$UAK_HOME` defaults to `~/.unreal-agent-kit`. Without a project, the fallbacks are `<EngineRoot>/Engine/Saved/AgentKit` and `$UAK_HOME/State/<engine key>`. A key is a hash of the normalised folder, so two projects never share a fallback folder, and neither do two engines. It also keeps state apart from the versioned `<version>/` install folders. Resolving it creates nothing; commands that write create it.
- **`uak env`** prints every resolved path, the bundled dotnet, the version-control system found, and how each was found.

## The queued lock (Locking)

`uak lock run [-name=] [-priority=High|Normal] -- <command...>` holds the lock around a command. `uak lock status` shows the holder and the queue. `uak lock forget-orphan -hold=<id>` drops a kept record of a dead holder's command (see "Command lifetime"). The library API is `await using var hold = await EditorLock.AcquireAsync(context, name, priority, ct)`.

- **The mutex itself** is an OS named mutex through `EpicGames.Core.SingleInstanceMutex`, named with `GlobalSingleInstanceMutex.GetUniqueMutexForPath("UnrealAgentKit_EditorLock", <scope key>)`, where the scope key is the scope folder's identity (see Scope), else its canonical path. The kernel releases it when its holder dies, so no dead-holder checks are needed. It is named `Global\…`, so it covers every session on the machine.
- **The queue** gives fair order and status, which the mutex lacks.
  - Waiters write tickets in `<State>/Lock/Queue/`, ordered by priority and then by arrival.
  - Only the head of the queue waits on the mutex.
  - A ticket whose process has died is removed. Liveness is checked by PID plus process start time, through `System.Diagnostics.Process`.
  - The holder writes `<State>/Lock/holder.json` for status only.
  - All files are JSON, UTF-8 without a BOM, with ISO 8601 UTC times.
- **Scope:** the mutex and the state directory derive from the canonical project directory (else the engine root), with junctions, links and subst drives resolved (Core's `CanonicalPath`). The mutex is keyed on the scope folder's identity (volume serial plus file ID; on Unix, device plus inode), so any path to the same folder, including a loopback UNC path or a mapped drive, gets the same lock. `uak lock run` refuses without a project unless `-engine-scope` is given (and refuses `-engine-scope` when a project was found). The holder logs the scope it locked, and `holder.json` records it.
- **Nesting:** while it holds, a holder sets `UAK_LOCK_HELD=<mutex>:<HoldId>` in its own environment, so its children (UBT, the editor, scripts) inherit it. A request for the same lock whose HoldId `holder.json` still records, with a live holder, joins that hold without waiting. Any other marker fails at once (lead's decision: a hold on one lock may not take another). Detached runs drop the marker.
- **Command lifetime:** `lock run`'s command runs in a kill-on-close job on Windows (a process group on Unix; TODO(unix) PDEATHSIG). Cancelling, uak dying or the command exiting stops its whole tree before release, except breakaway or detached runs. `lock run`'s job is named after the HoldId, and `holder.json` records `CommandPid`, `CommandProcessStart` and `CommandJob`. `uak build` and `uak test` record their child's PID the same way. A new holder that takes the mutex from a dead holder of the same scope waits up to 30 s, while that command lives or its job still has processes, then warns. A record of another scope (for example another project's, in a shared folder) is never waited for. `holder.json` lasts one hold (the next holder writes over it, and a release deletes it), so a holder keeps a command that outlived that wait in `<State>/Lock/Orphans/<HoldId>.json` (`OrphanRecords`, 0.4.1, the dead holder's record, written only by a holder, before it writes `holder.json`). Every later hold waits for the kept commands too, up to 30 s for them all, warns and reports them (`IOrphanedCommandHold.OrphanedCommand`; a nested hold reports them without waiting); `uak lock status` lists them; and `uak mutate` and `-restore` refuse, each time, until the command has gone. A record is dropped only then, or by hand (below): the process with that PID and start time has gone (a reused PID doesn't count as it; a start time read within 60 s of the record's does, `EditorLock.CommandStartTolerance`, as a clock step shifts it on Linux, where a zombie counts as gone) and its job is empty (`EditorLock.IsCommandRunning`). So a hung orphan costs every hold 30 s, and refuses `uak mutate`, until someone stops it, which is what the warning says; nothing waits for it for longer. The other way out is `uak lock forget-orphan -hold=<id>`, for a record nothing would ever end: a reused PID whose start time can't be read counts as a match (`ProcessIdentity.StartTimesMatch`), and so as the command, and off Linux a zombie still reads as running. It takes the lock (with no wait for the commands; a dead holder's record in `holder.json` is kept first, as by any hold), drops that record, says what it dropped and the PID, and stops nothing; an unknown ID exits 2 and lists the kept IDs. The refusals of `uak mutate` and `-restore`, the hold's warning and `uak lock status` name it, with the hold's ID (`IOrphanedCommandHold.OrphanedHoldIds`, `EditorLock.DescribeForgetOrphan`), say the PID may have been reused, and say to use it only once the process is known to be gone or its PID known to be reused, as a build that really still runs could write mutant objects past the stamp. Waiting and warning, not refusing, is what the other commands do, as a hold that could never start would stop every agent. Scope and machine rules are as for `holder.json`: another scope's or machine's record is neither waited for nor deleted.
- **Versions:** the mutex name depends on the kit version's scope rule, so all agents on one machine should use the same `uak` version.
- **Tickets:** the sequence is wall-clock ticks raised above every queued ticket and this process's last, so it only grows. Another machine's tickets and holder are reported, never waited for or deleted.
- **Quiet holds** (0.4.0, `uak test -quiet`, for benchmarks): `holder.json` records `Quiet`. `uak compile`, which takes no lock, records a marker in `<State>/Lock/Compiles/` while it runs and, before it starts, waits while a live quiet holder holds the lock (for at most 30 minutes, `QuietRuns.DefaultQuietWaitTimeout`, saying every 5 minutes that it still waits; then it compiles with a warning, its marker written, so a hung or hours-long quiet run never stops compiles for good); the quiet holder, once it holds, waits until no live marker is left, for at most 10 minutes (`QuietRuns.DefaultCompileWaitTimeout`; then it goes ahead with a warning, as it holds the lock while it waits). Each writes before it reads (the compile its marker, the holder `holder.json`), so of two that race, one sees the other. A quiet holder and a compile marker are live only when their process surely runs (`ProcessIdentity.IsSurelyAlive`: both start times read and matching), so a killed one whose ID a protected process reuses never stops compiles; a dead compile's marker is deleted, never waited for; a compile inside the quiet hold itself (it inherited the hold's marker) doesn't wait. A quiet run refuses to start (exit 2) while others wait in the queue, and inside another hold that isn't quiet (exit 2: a joined hold can't set the holder's flag); it fails (exit 1) when it can't write `holder.json`, which is how compiles learn of it.
- **Priority** takes effect within one poll (1 s): a High waiter takes the front from a Normal waiter already waiting there, which cancels its mutex wait and goes back in line.
- **Defaults:** an explicit priority beats `UAK_LOCK_PRIORITY`; callers pass null to inherit it. Inside a run, a lock's name shows as `<UAK_LOCK_NAME>/<name>`. `holder.json` carries a HoldId, so a holder only deletes its own record.
- **Abandonment is normal.** `SingleInstanceMutex.Dispose` doesn't wait for its own release, so every handoff looks like an abandoned mutex. Its waiters, and UBT's, treat that as success. We keep Epic's class (lead's decision, 2026-10-01). A non-kit waiter on our mutex name would see `AbandonedMutexException`.
- **One machine:** the queue is per machine, because the mutex is. The state directory must be local. Tickets and `holder.json` record `Machine`.
- **Platform check:** on Linux and Mac, .NET named mutexes work between processes of the same user. This needs testing on those platforms later. Unix doesn't delete tickets on a crash, so dead-ticket cleanup covers it there.
- **Tests:** real separate processes, checking:
  - first-in, first-out order;
  - priority;
  - a dead waiter;
  - a dead holder (the mutex is abandoned);
  - no overlap, checked through an enter/leave log;
  - cancellation.

## Detached runs (Runs)

- `uak runs start -name= -owner= [-priority=] [-result-file=] [-output=] [-force] [-allow-sleep] -- <command...>` starts a run. It waits up to 30 s for the wrapper to record itself, and exits 1 if the wrapper exits first.
  - The run survives the end of the caller's shell and a restart of the agent session.
  - **Keeping the machine awake** (0.3.1): the wrapper keeps the system and the display on for the whole run, unless `-allow-sleep` (recorded as `AllowSleep`). A laptop that sleeps, or enters Modern Standby, under a long build or a GPU-heavy editor run can lose the run, or stop the machine: a 0x19C power watchdog bugcheck was seen that way. On Windows it is `SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED | ES_DISPLAY_REQUIRED)`, from a dedicated thread, because the request belongs to the thread that made it (`KeepAwake`). It ends with that thread, or with the process. A refused request is written to the run's output. It doesn't stop a closed lid from sleeping the machine. Linux and Mac: not yet (TODO: `systemd-inhibit`, `caffeinate`).
  - It is recorded in `<State>/Runs/<name>.json`, with output in `<name>.log`.
  - The run takes the lock only if the command itself does.
  - `-priority` passes `UAK_LOCK_PRIORITY` to the child, and the lock's name defaults to `UAK_LOCK_NAME`.
- `uak runs show -name=<exact name>` (0.4.0) prints a finished run's end (as `runs wait` does) and the summaries its `uak build`, `uak test` and `uak mutate` recorded, oldest first, without reading its output. The wrapper sets `UAK_RUN_NAME` for its command and deletes the run's old summaries when it starts. Each of those commands records in `<State>/Summaries/<name>.json`, under its own `-name=` (so `runs show` also works for a direct `uak test -name=`) and, inside a run, added under `UAK_RUN_NAME`. Each entry names the command run that recorded it (`RunSummaryInvocation`: a new ID per run of a command, which `SummaryWriter.RecordingAsync` keeps in an `AsyncLocal` for the command's own `Record`, and the process's ID and start time). As it starts, a command drops its own name's results, and the entries of commands under it whose process no longer runs, and adds an entry with no exit code (`RunSummaries.Begin`, from `RecordingAsync`, which reads `-name=` before anything else is checked), so an earlier command's result under that name is never shown as this one's; at its end, the lines it printed, in its own entry's place (`RunSummaries.IsOwn`: the same ID; an entry recorded without an ID is no command's own, so it never takes another's place), never another's; and when it is refused or fails first, a `REFUSED` (exit 2) or `STOPPED` (exit 1) line, only where its own entry still has no result. So two commands that run under one name at once (the default names `uak-build`, `uak-test` and `uak-test-cooked` are every command's that has no `-name=`; `Begin` runs before the lock, while a command waits for it) each keep their own entry: `runs show` lists them all with their process IDs and says that several ran under the name at once, and, when one is a test or a mutation check, that they share the test log named after the name (`<Project>/Saved/Logs/<name>.log`, and the folder of a cooked run), which each test run replaces as it starts, so an earlier one's `Log:` line may name another's log. A command killed before it recorded a result leaves its entry without one: `runs show` says it "recorded no result", and whether its process still runs (`RunSummaryEntry.MayStillRun`: `ProcessIdentity.IsSurelyAlive`, so an unknown start time counts as gone and a reused ID never keeps a stopped command's entry), and `runs wait` prints `Verdict: none`; each write reads, adds and writes under a gate file (`<name>.json.lock`, opened for one process alone), so two commands of one run that end together keep both. Runs and commands share the names: a direct `-name=X` drops run X's results, and `uak runs start -name=X` clears command X's. A name is any plain file name without white space, control characters, path separators or `: * ? " < > |`, that doesn't end in `.` (Windows would drop it, so `X.` and `X` would share a file and a journal folder) and isn't a Windows device name (`CON`, `NUL`, `COM1`, ..., with or without an extension) (`RunSummaries.IsValidName`): `uak test`, `uak build` and `uak mutate` (and `MutationJournal.Begin`) refuse any other `-name=`, and `runs show` takes any such name or any run's. A summary that can't be written is a warning, never the command's failure.
- `uak runs list [-all] [-name=<pattern>]` and `uak runs adopt -pid= -name= -owner= [-output=] [-result-file=]`. `runs list` shows only running runs by default and always exits 0, so it can't tell a waiter when a run ended.
- `uak runs wait -name=<exact name> [-timeout=<seconds>]` reads the run's record every 5 s until the run has ended, then prints its end state (with its exit code), how long it ran, its last line, the verdict line of its last recorded summary with that command's exit code (`Verdict: mutate 'M1' exited 6: ...`), and its output file. Its own exit code is 1 for any code but 0, so a command whose codes carry results (`uak mutate`) is read from the printed code and line.
  - Exit code 0 when the run exited 0; 1 when it exited with another code, or ended with no recorded exit code (an adopted run, one that died, or one that never started), which it says; 2 for a usage error or no such run; 3 when `-timeout` passed while the run still runs.
  - A record that exists but can't be read (it is being rewritten) is read again on the next poll.
  - **How agents wait:** one background shell runs `uak runs wait -name=<name> -timeout=<seconds>`, with its own time limit longer than `-timeout` and within the shell's two-hour limit. It costs nothing while it waits, and its end wakes the agent. On exit 3, the agent starts another wait. Agents never poll a run themselves, and anything that may run over an hour goes through `uak runs start`.
- **Starting safely:** a run's name is claimed with `<Name>.claim` (create-new, delete-on-close) around the name check and the first record write, so concurrent starts of one name start one run. The output is emptied on every start. Bare program names resolve on PATH only; a missing one fails the start, and the failure is recorded.
- **Detaching:**
  - Windows: `CreateProcess` with `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP | CREATE_BREAKAWAY_FROM_JOB`, falling back without breakaway when the job refuses it.
  - Unix: a new session, using `setsid` through P/Invoke, or an equivalent.
- **Recording the end:** a hidden wrapper mode (`uak runs _wrap`) records the end time, exit code and last line.
  - The wrapper gets no inherited handles. It opens the log itself and hands it to the command, so no shell pipe is held and the output survives the wrapper.
  - Its own log lines start with `UakRun '`, and last-line reading skips them.
  - The wrapper retries the end record, and falls back to a log line if it still can't write it.
  - A running wrapper keeps its `uak` install's files open. That's harmless for versioned installs, but a dev build of uak can't be rebuilt while a run is going.
- **Record fields:** Name, Owner, Pid, ProcessStart, Command, Arguments, CommandLine, OutputFile, ResultFile, Priority, Adopted, Started, Ended, ExitCode and LastLine, plus the optional `WorkingDirectory`, `Detach` (`breakaway`, `job` or `session`) and `AllowSleep`.

## Version control (Vcs)

`IVersionControl : IDisposable` covers:
- `Kind` (Git, Perforce or None) and `RootDirectory`;
- `GetCurrentRevisionAsync` (git: commit hash; p4: the newest submitted change the workspace has);
- `GetChangedFilesAsync` (git: modified, staged and untracked files; p4: files opened in the client only, so files edited offline are not found), with an optional path filter;
- `GetFileStatusAsync(paths)`, which returns one entry per path, in the order given. The states (`VcsFileState`) are Unknown, Unmodified, Modified, Added, Deleted, Renamed, Copied, TypeChanged, Conflicted, Untracked and Ignored. Perforce never reports Conflicted, because fstat has no "unresolved" tag;
- `IsIgnoredAsync(path)` (git: `check-ignore`; p4: `add -n`);
- `DescribeAsync()` (a one-line summary for `uak env`).

Writes are Perforce only, on the side (`PerforceVersionControl`, not `IVersionControl`), and stop at shelving: nothing commits, submits or reverts (see "Perforce writes").

- **Detection,** in this order:
  1. `-vcs=`, or the `UAK_VCS` environment variable. Values: `git`, `perforce` (or `p4`), `none`. `-vcs=` is a global option that Core resolves into `UakContext.RequestedVersionControl`, and the vcs commands also accept it locally;
  2. a `.git` directory, or `.git` file, above the project;
  3. a Perforce workspace: a `P4CONFIG` file at or above the start directory. A global P4PORT or P4CLIENT alone is not used and p4 is not run; `-vcs=p4` uses them;
  4. otherwise None.

  It starts from the project directory, then the engine root, then the working directory. The API is `VersionControlDetector.DetectAsync(context)`, which returns the implementation and its provenance. `uak env` reports it through `VcsEnvReporter : IUakEnvReporter`.
- **Implementations** (git and p4 are found on PATH only, never in the current or application directory):
  - Git, through the `git` command line (`-C <root>`, `GIT_TERMINAL_PROMPT=0`, `GIT_OPTIONAL_LOCKS=0`).
  - Perforce, through `EpicGames.Perforce` (see "Engine libraries").
- **git time limit:** every git command has a time limit (`UAK_GIT_TIMEOUT`, 30 s); git is stopped and the command fails with a `VcsException` that names the variable.
- **Perforce safety:** every p4 command has a time limit (`UAK_P4_TIMEOUT`, 15 s). When detection couldn't reach the server, `uak env` reports that instead of asking again. File arguments are escaped (`@`→%40, `#`→%23, `%`→%25, `*`→%2A), a path containing `...` is rejected, and `add -n` takes the raw name with `-f`.
- **Commands:** `uak vcs status [paths...]`, `uak vcs changed [-path=]` and `uak vcs revision`, each with `-json`. Data goes to stdout and errors to the logger, so `-json` output is safe to parse.

### Perforce writes

`uak vcs edit|add|reopen <file>... [-c=<changelist>|default]`, `uak vcs change new -description=`, `uak vcs change describe -c= -description=`, and `uak vcs shelve -c=<changelist> [-keep-unopened]` or `uak vcs shelve <file>... [-description=] [-force]`. Each takes `-json` and `-vcs=`. In a Git workspace, or with none, they are usage errors that say "Perforce only".

- **Only this client's pending changelists.** A target changelist is read with `p4 change -o` first; one that is submitted, unknown, or another client's is refused before anything changes.
- **Checked afterwards.** edit, add and reopen ask `p4 fstat -Ro` which client changelist each file ended in; exit 0 only when every file is where it was asked to be. A file p4 left elsewhere (already opened in another changelist; not on the client; ignored by P4IGNORE) is reported with p4's own message.
- **Named files.** Wildcards (`...`, `*`, `?`) are refused. Directories are refused unless `-folders`, for edit and reopen only: a directory also takes every other file opened under it. Half of a move (move/add or move/delete, from fstat's movedFile) is refused for reopen and shelve unless the other half is named too, because p4 moves both halves together.
- **Client names** compare exactly; names that differ in case alone match only when `p4 info` says the server ignores case (caseHandling). Paths must be inside the client root. add refuses files that don't exist (p4 would open them for add anyway) and passes names holding `@ # % *` raw with `-f`; the others escape them.
- **Descriptions.** `change describe` sends back the whole `p4 change -o` record (its files, jobs and every other field) with only Description replaced: a spec without its Files field moves the files out of the changelist ("updated, removing N file(s)"). p4 makes the changelist hold the spec's files, so files that changed changelist between the read and the write move: one reopened into it meanwhile goes out to the default changelist ("removing"), and one moved from it to the default changelist comes back in ("adding"). A file moved to another numbered changelist makes p4 refuse the whole spec (found on a real p4d), which fails the command with nothing changed. uak lists the changelist's files just before the write and after it (`p4 opened -c <N>`), and the default changelist's after it. It moves back only files that were in the changelist just before the write (or are in the spec) and are now where p4 put them, never unrelated files that reached the default changelist meanwhile, and only when their numbers are the counts p4 reported. Otherwise it can't tell which files p4 moved, so it moves none and fails, naming what it found. What it moved back is checked and reported (`restored`, `released`). `change new` sends Change "new", the client and the description, with no Files, so nothing moves into it.
- **Shelve.** `-c=` runs `p4 shelve -r -c<N>`, which makes the shelf exactly the opened files, after checking that something is opened, since `-r` with nothing opened would empty the shelf. `-keep-unopened` runs `p4 shelve -f -c<N>` instead (the default before 0.3.3), which shelves the opened files over their shelved copies and keeps every other shelved file. `-r` is the default because with `-f`, files that were reverted or moved out of the changelist stay on the shelf: a preflight builds them, and a Horde auto-submit submits them. `-replace` and `-drop-unopened`, which asked for `-r` before 0.3.3, are accepted and ignored. uak reads the shelf before and after (`p4 describe -S -s`):
  - `-r` deletes shelved files that are not opened in the changelist. uak lists them first (shelved, and not opened when it read the changelist) and prints each one the shelf loses ("REMOVED from the shelf", `removed` in the JSON); a shelf that is the only copy of such work needs `-keep-unopened`. A file the shelf lost that uak had not listed (it left the changelist between uak's read and p4's shelve) fails the command (exit 1), naming it: its shelved content is gone from this shelf, and nobody saw it go.
  - Every file the shelf loses is printed; so is every shelved file that changed (`replaced`: its digest or its action changed, or a digest appeared or went), and every shelved file `-f` kept although it is no longer opened in the changelist (`kept`: a submit of the shelf would include it). `-json` carries all three.
  - When the shelf can't be read afterwards, the command fails, saying the shelve ran and, for `-r`, naming the shelved files that were not opened when uak checked (those `-r` deleted).
  - **Auto-submit guard.** Before it changes an existing changelist's shelf, `vcs shelve -c=` asks every `IPerforceShelveGuard` the host loaded (found by reflection, like `IUakEnvReporter`, so Vcs never references Horde). AgentKit.Horde's guard refuses (exit 1) while an auto-submit preflight of the changelist is running: when it succeeds, Horde submits the change's current shelf (HordeServer.Build's JobService passes the change itself as both the shelved and the original change, so its digest check compares the shelf with itself), so a new shelf would be submitted unbuilt. With no Horde server configured it checks nothing; it never opens a sign-in page; when Horde can't be asked (not signed in, unreachable, no answer in 60 s), uak warns and shelves.
  - **Mutation guard** (0.4.0). While a `uak mutate` journal is left (`MutationFolders.DescribeLeft`, in AgentKit.Core: a folder under `<State>/Mutations` holding a `journal.json`, a copy or contents that can't be listed), a running or a killed check's patch may be in the files, and a shelf would ship it (an auto-submit would submit it). Since 0.4.1 a journal whose record reads phase `Restored` (its files are back: each holds its original bytes, or an edit made since with the mutation taken out) is left out (`MutationFolders.ListLeft`, which believes the phase only when the record names its folder's run and each file it lists has a full path): only the binaries may still hold its patch; one that can't be read is still in. A project may version its binaries, so a shelf that holds one of those is refused all the same (`MutationFolders.DescribeBinariesIn`, by file name, a depot path saying no more; any code file when the journal doesn't know which it wrote), by `vcs shelve` (exit 2 for files named, exit 1 for `-c=`, read just before p4 shelves) and `uak horde preflight -shelve` (exit 5). `vcs shelve` refuses (exit 2) before it reads or creates anything, and checks again just before `p4 shelve` (then exit 1, naming a changelist it created); `uak horde preflight -shelve` refuses (exit 5) first and again just before shelving. `vcs status` and `vcs changed` warn on the log (so `-json` stays clean), naming each journal and its files. `vcs change new` and `describe` move no content and aren't checked. A commit is the lead's: the workflow skill has it wait for `uak mutate -status` to exit 0.
  - With files instead, uak first checks every file is opened here (or changes nothing), refuses files in a numbered changelist (they would leave it; `-force` moves them) and half moves, then creates a changelist, reopens the files into it, checks them, and shelves it; it prints each file's original changelist. "Created change N." is printed at once (on standard error under `-json`), and a failure after that names the changelist and the files it holds.
  - Shelving may take up to 30 minutes (`PerforceVersionControl.ShelveTimeout`), because it sends file contents; queries keep `UAK_P4_TIMEOUT`.
- **Records.** EpicGames.Perforce has no typed record for some of these answers (its ReopenRecord has no fields), so `PerforceRawRecord` reads every field of each record through the library's own `PerforceOutput.ParseRecord`, and writes specs back with `PerforceRecord.Serialize`.
- **Tests** use recorded answers of a real p4d (fixtures), and an opt-in test runs every write against a throwaway local p4d over `rsh:` (`UAK_TEST_P4D`, the path of a p4d program).

## Horde

`uak horde config|login|logout|streams|templates|preflight|job|log`, in AgentKit.Horde, on EpicGames.Horde (see "Engine libraries").

- **The server** comes from `-server=`, then `<UAK_HOME>/config.json`'s `horde.server` (shared by every kit version; `uak horde config -server=` writes it, atomically, keeping other settings), then Horde's own default (`UE_HORDE_URL`, the registry value Horde's tools write on Windows, `~/.horde.json` elsewhere). With none, the commands fail with a message telling the agent to ask the user (through the lead) for the URL.
- **Sign-in.** A command first gets a token silently (Horde's token cache, refreshed without a prompt; `AllowAuthPrompt` off). When that fails, it opens the Horde sign-in page in the browser, in that process, and waits up to `-login-timeout` (600 s), then exits 4. `-no-login` never opens it. The sign-in waits on the library's auth state directly (`GetAccessTokenAsync(true)`), not inside an HTTP request, so HttpClient's 100 s time-out doesn't cut it short: `-login-timeout` is the real limit. EpicGames.OIDC stores only the refresh token, so if the identity provider rejects the silent refresh (for example Entra ID's AADSTS90009), each process would sign in again; uak's token cache (below) bridges that, and the user should ask the Horde admin to check the server's OIDC scope. `uak -verbose` shows the library's own messages.
- **Stream and template.** The workspace's client stream, then its parents up through virtual streams to the first non-virtual one (a shelf holds that stream's paths), matched as Horde's dashboard does: by name, then by id (the name without `//`, `/` as `-`, lower case), then by name plus `-VS`. The template: `-template=` (id or name, must allow preflights), else the stream's default preflight template, else its only runnable preflight template. Streams and templates are read into uak's own records: the library's response classes can't be deserialized.
- **Starting a preflight.** EpicGames.Horde's own `CreateJobRequest`, serialized with its own settings: `PreflightCommitId`, `UpdateIssues = false`, `AutoSubmit` only with `-autosubmit` (which tells Horde to edit the change's description and submit it when the preflight succeeds; the usage text and output say so). Job creation isn't idempotent and the library's HTTP handler retries, so the POST goes once through a plain HttpClient with the bearer token. Before shelving or creating anything, uak lists the change's preflights. When an auto-submit preflight succeeds, Horde submits the change's CURRENT shelf, whatever shelf the preflight built (HordeServer.Build's JobService passes the change itself as both the shelved and the original change), so:
  - **`-shelve`** shelves as `uak vcs shelve -c=` does: `p4 shelve -r`, so the shelf becomes exactly the opened files and shelved files no longer opened in the change are deleted from it (each is printed), and nothing reverted or moved out is built or auto-submitted; `-keep-unopened` uses `p4 shelve -f` instead and keeps them. It never reuses a preflight (a new shelf needs a new build), and refuses (exit 5) to shelve while an auto-submit preflight of the change is running, checked before anything else and again just before `p4 shelve`. With `-keep-unopened -autosubmit` it also refuses when the shelf holds files that are not opened in the change (`p4 shelve -f` keeps them, and Horde would submit them too), checked before shelving; with or without `-keep-unopened`, the shelve's `kept` files are checked again afterwards (then the change is shelved, but nothing is started). `-allow-shelved-only` lets the user accept that, and needs `-keep-unopened`: without it the files would be deleted, not submitted, so a script that asked for them to be submitted gets a usage error instead of losing them. The shelve's lines (shelved, replaced, removed, kept) go to standard error under `-json`, and the JSON carries `shelved`, `replaced`, `removed` and `kept`.
  - **Reuse.** Without `-shelve` (and without `-force`) uak reports a still-running preflight instead of starting another ("reused: <job>") only when all of these hold: uak started it (it records each preflight it starts, with the change's shelf then: `<UAK_HOME>/horde/<server>/preflights/<job>.json`, kept 30 days); it has the same stream, template, auto-submit setting and every parameter value (the job's reported parameters against the template's defaults with uak's values over them), and no additional arguments or targets; it was created at least 5 s after the change was last shelved (`p4 change -o`'s shelveUpdate, in the server's time zone from `p4 info`'s tzoffset; unknown without tzoffset); and the change's shelf (`p4 describe -S -s`: each file's action and digest) is the one uak recorded. The shelve time has 1 s resolution and tzoffset is the server's offset now (a daylight-saving change since the shelve moves it), so the recorded shelf is the real check and the time a second one. When any of that can't be read, it starts a new one. Horde's `arguments` can't be compared: Horde fills them in from the parameters (JobsController), and uak never sends its own.
  - **Auto-submit.** `-autosubmit` is refused (exit 5) while another auto-submit preflight of the change is running, unless that is the one reused, `-force` or not: both would submit the change. Without `-autosubmit`, a running auto-submit preflight is a note; when it was created before the change was last shelved, or uak can't tell (or uak recorded another shelf for it), a WARNING that Horde will submit a shelf it may not have built.
  - The line naming the template and parameters, and the auto-submit state, describe the job actually reported. After a create that fails without a clear answer, uak looks for a new job of exactly this request (the reuse comparison, without the shelf) before reporting the failure.
- **The job URL** (`<server>/job/<id>`) is printed as "Job URL: ..." the moment the job is created or found, before any wait (standard error under `-json`), so it survives a failure, a time-out or Ctrl+C. Agents send it to the lead at once.
- **Results** follow Horde's own rule (JobExtensions.GetTargetState): the latest step per node; any failure fails the job, else warnings, else skipped or aborted steps (or a batch that couldn't run) leave it incomplete, else success. The summary lists only failing steps and those with warnings, with their step and log URLs; `-verbose` lists every step.
- **Waiting** (`-wait`) polls with `modifiedAfter` (an unchanged job is an empty answer), every 15 s, backing off to 60 s while nothing changes; prints one line when the job starts running and one when Horde can't be reached; survives transient errors (no connection, time-outs, 408, 429, 5xx); and stops at `-timeout`. After 4 transient failures in a row it rebuilds its client (a fresh connection): a client on uak's cached token keeps that token, any other gets Horde's own token handling again (which refreshes itself), never a copy of the access token, which would expire mid-wait. A 401 on a rebuilt client signs in again once, as for a refused cached token (below). A sign-in after a 401 mid-wait may take only the time the wait has left before `-timeout` (none left: no sign-in, exit 4). A time-out before any poll got an answer is "still running" too (3). Exit codes: 0 success, 1 failure or incomplete, 2 usage error (uak's own, before anything is sent), 3 still running, 4 not signed in, 5 another error (including 403, not allowed; uak's own refusals to shelve or auto-submit while an auto-submit preflight runs, or to auto-submit shelved files that aren't opened; and any answer uak can't read: never mistaken for a job result), 6 (preflight) build settings needed, 7 success with warnings.
- **Errors and warnings** (`uak horde log -job=<id>`, and `-issues` on `horde job` and `preflight -wait`) come from Horde's log events (`GET api/v1/logs/{id}/events`, EpicGames.Horde's GetLogEventResponse: a severity, a line index and count, and the structured lines), not from the log's text: Horde already classed each event when the log was written, so uak never greps logs. Events are read in pages of 250, at most 5000 per log (more is reported as truncated). Without `-step=` the steps are the failed ones, then those with warnings (latest step per node). Within a step, events are grouped by severity and text, after removing Unreal's `[time][frame]` prefix, which differs on every line; a group shows its first occurrence and its count. A group already shown under an earlier step is only counted. Errors come first, then warnings, each in log order, at most `-max=` (default 10) per step; the rest are counted. Lines are capped at 300 characters and events at 12 lines. Context is the log lines before an event (`api/v1/logs/{id}/lines`; default 2 before errors, none before warnings) and is left out when it can't be read (a text log's lines endpoint doesn't return JSON). A step whose events can't be read gets a note; only a refused sign-in or a cancel stops the command. `-save` streams a step's whole log as text (`api/v1/logs/{id}/data?format=Text`) to `<State>/Logs/horde/<job>/<step name>-<step id>.log`, through a temporary file. The exit code is the job's result, as `uak horde job` reports it, never a property of the log.
- **Build settings.** A preflight's template and parameter values are saved per user, server and Horde stream, in `<UAK_HOME>/horde/<server>/<stream>/templates.json` (`<server>` is the host, then the port and path segments joined by `_`): the chosen template and each template's values, written atomically, keeping keys uak doesn't know. `uak horde config -template= -param:<id>=` saves them after checking them against the server's template (ids, bool values, list choices, a text's regular expression); `-reset-build` forgets them. Parameters come from the stream list's templates (Bool, Text and List; a List has no id in Horde, only its choices, so uak names it from its label). Values go to Horde as `CreateJobRequest.Parameters`: a bool or text by id, a list as every choice's id with "true" or "false". With nothing saved and no `-template=`/`-param:`, or with saved settings that no longer fit the server's templates, a preflight starts nothing and exits 6, printing the templates as `uak horde templates -json` does, so the lead can ask the user (agents can't answer prompts on standard input). `-use-template-defaults` skips this for CI.
- **Token cache.** EpicGames.OIDC keeps only refresh tokens; when a server refuses refreshes, every process would sign in again. So on Windows uak keeps the access token per server in `<UAK_HOME>/horde/<server>/token.bin`: JSON with the server and the expiry (the JWT's `exp`; no expiry, no cache), encrypted with DPAPI for the current user (CryptProtectData, the server's URL as entropy), written atomically (last writer wins). It is passed as `HordeOptions.AccessToken` while more than 5 minutes are left. A 401 on it deletes it, signs in afresh, and retries only the request that failed, once (`HordeApiSession`; a 401 means the server refused before doing anything): a preflight is never shelved or created twice, and a wait keeps its job and its deadline. A token EpicGames.Horde takes from the environment (`UE_HORDE_TOKEN` for the `UE_HORDE_URL` host) is neither replaced by the cache nor saved in it. `uak horde login` checks a cached token with the server before saying it is signed in. An unreadable file is ignored and replaced. `uak horde logout` deletes it. Other platforms cache nothing. The token is never printed or logged.
- **Opening pages.** `horde.open` in the config (`uak horde config -open=never|created|finished|failed`, default never) opens the job's page, or the first failed step's, in the default browser during `-wait`; `-no-open` skips it once. A failure to open is one warning.

## Unreal operations (Unreal)

- **`uak compile <file>... [-dependents] [-target=] [-config=] [-platform=] [-MaxParallelActions=] [-maxerrors=] [-resultfile=] [-- <UBT option>...]`** checks files through UBT's single-file compile (`-SingleFile=`, given as a file list) for the project's editor target (`<Project>Editor`, else the `Editor` target in `Source/*.Target.cs`, else `UnrealEditor`), with the platform's real compiler. A `Type = TargetType.Editor` inside a `//` or `/* */` comment doesn't count. Nothing is linked, and objects go to a separate `SingleFile/` folder, so it is safe while an editor runs.
  - UBT compiles a header on its own, through a generated `<Name>.h.cpp`, so headers must be self-contained (lead's decision, 2026-10-01: keep this strict default). `-dependents` adds `-SingleFileBuildDependents`.
  - UBT silently drops a file that isn't in the target, or a header marked HEADER_UNIT_SKIP, and skips a file whose `SingleFile` object is newer. So uak first deletes the requested files' old `SingleFile` objects (only under the project folder), then checks that a compile action ran for each file. A file that didn't compile is NOT COMPILED, exit code 2.
  - The files go to UBT in a list file, `-FileList=<State>/Logs/compile-<UTC time>-<pid>.files.txt` (one full path per line, UTF-8, kept beside the log), not as one `-SingleFile=` each (since 0.2.4). UBT reads the list into the same list `-SingleFile=` fills, before `-SingleFileBuildDependents` expands it, so it is one UBT run, as before, for any number of files. One option per file broke on a source build: about 150 files passed cmd.exe's 8191-character limit for `Build.bat` ("The command line is too long"). UBT reads no `@response` file, and splitting into batches would run UBT, and with `-dependents` the dependents, once per batch. `-FileList=` reads the same in UE 5.5, 5.6 and 5.7.
  - It passes `-WaitMutex`, and does not take the editor lock. UBT's own mutex already makes compile checks run one at a time. It waits only while a quiet run holds the lock (see "The queued lock"). Since it takes no lock, it judges mutation journals itself (`MutationJournal.CheckForCompile`): it refuses (exit 2) while a stopped run's journal that isn't Restored, or one it can't read, is left, and warns, naming the files, while a run whose process surely runs has its patch in the tree. A folder it can't read is looked at again every 50 ms for up to a second before it refuses (`MutationJournal.ListSettled`): a live run may be saving its journal.
  - **Memory** (0.4.0): with `-dependents`, a given `-MaxParallelActions` (or `UAK_MAX_PARALLEL_ACTIONS`) is lowered to one action per 1.5 GiB of free memory, at least one. That is UBT's own rule (UE 5.8 `UnrealBuildTool/System/Utils.cs`, `GetMaxActionsToExecuteInParallel`, with `UnrealBuildAcceleratorConfig.MemoryPerActionBytes`), which UBT applies only to its own default: a given value turns it off. Free memory is measured as EpicGames.Core's `SystemUtils.GetFreeMemoryBytes` does (the GC's total available minus its memory load; Mac: the total). A target's larger `MemoryPerActionGB` isn't read.
  - UBT options after `--` are checked as for `uak build`. `-SingleFile`, `-File`, `-Files`, `-FileList` and `-SingleFileBuildDependents` are rejected too: uak sets them, and UBT reads the first four into one list of files, which would add files uak does not report on.
  - It prints errors as `file(line): error: CODE: message`. A header error repeated across translation units is reported once, with a count.
- **`uak build [-target=] [-config=Development] [-platform=host] [-MaxParallelActions=] [-maxerrors=] [-resultfile=] [-- <UBT option>...]`** runs under the editor lock. On an installed engine it runs UBT directly on the bundled dotnet; on a source build it runs the platform's Build script, which rebuilds UBT when needed. It always adds `-WaitMutex` and `-NoHotReloadFromIDE`.
  - **UBT options after `--`** (for example `-DisableAdaptiveUnity` or `-Module=<name>`) go to UBT as given, after uak's own (`UbtCommandLine.CheckPassThrough`). Each must be an option: UBT reads a bare word as another target, platform or configuration.
  - Options uak sets, or that would break its guarantees, are rejected: `-Project`, `-Target`, `-TargetList` and `-Mode` (what is built, and that it is a build); `-WaitMutex` and `-NoMutex` (UBT's one-instance mutex); `-NoHotReloadFromIDE`, `-ForceHotReload` and `-LiveCoding` (never patch a running editor); and `-MaxParallelActions` (use uak's option). Names match in any case, as UBT reads them. A rejected option is a usage error (exit 2), before the lock is taken.
- **`uak test -filter=<filter> [-expect=<file>] [-gpu | -windowed [-resx=] [-resy=]] [-name=] [-resultfile=] [-- <editor argument>...]`** runs the editor with `-ExecCmds="Automation RunTests <filter>;Quit"` (`-nullrhi` unless `-gpu` or `-windowed`) under the lock.
  - **Windowed runs** (`-windowed`, for tests that need a real viewport and Slate windows) start the editor itself, not its `-Cmd` (`EditorLocation.Executable`: the receipt's `Launch`, else the editor beside the `-Cmd` one). They pass `-windowed -ResX=1600 -ResY=900` (`-resx=` and `-resy=` change the size) instead of `-nullrhi` or `-RenderOffscreen`.
    - A window opens on the desktop, so it needs an interactive session.
    - Pass and fail are decided as for any run: from the log (`-abslog`), the report and the `-testexit` exit.
    - On Windows the windowed editor is a GUI program and writes nothing to its console, so a crash before the log has no last output to show.
    - `-gpu` and `-windowed` together, or `-resx=`/`-resy=` without `-windowed`, are usage errors.
  - **Editor arguments after `--`** (for example `-SCCProvider=None`) go last, as given (`EditorTestCommandLine.CheckPassThrough`). Those uak sets are rejected, written `-Name`, `--Name` or `/Name`, in any case:
    - `-ExecCmds`, `-testexit`, `-abslog` and `-ReportExportPath`: uak's checks depend on them, and the engine reads only the first of each (FParse::Value), so a second one would be ignored silently;
    - `-nullrhi`, `-RenderOffscreen`, `-windowed`, `-ResX` and `-ResY`: these are uak's `-gpu`, `-windowed`, `-resx=` and `-resy=`.
  - **Which editor:** the project editor target's build environment decides it (`EditorLocator`, Core).
    - A shared environment, the default for a modular editor, runs the engine's `UnrealEditor-Cmd`.
    - A unique one runs `<Target>-Cmd` from the project's `Binaries/<Platform>`. UEBuildTarget.cs names the binaries after the target, and puts them under the project when the `.Target.cs` is there.
  - **Why the receipt:** the `.Target.cs` text can't tell the two apart. A base class in another file can set the environment, as can `-UniqueBuildEnvironment`, and UBT settles `UniqueIfNeeded` only by compiling the rules.
    - So uak reads the target receipt UBT writes when it builds the editor, `<Project or Engine>/Binaries/<Platform>/<Target>.target`. Its `TargetBuildEnvironment`, `Launch` and `LaunchCmd` are UBT's own answer.
    - Without a receipt, uak takes a built `<Target>-Cmd` if there is one, then a `BuildEnvironment = TargetBuildEnvironment.Unique` in the target file itself, then the shared editor.
    - `uak env` shows both editors (cmd and windowed) and how they were found.
    - UBT's `-Mode=JsonExport` would also answer, but it compiles the rules and builds the target graph under UBT's mutex: too slow for every run.
  - The log is `<Project>/Saved/Logs/<name>.log`, deleted before the run. The report goes to `<State>/TestReports/<name>`.
  - A run passes only when all of these hold: tests were found; the found count equals the completed count; none failed; at least one passed (all skipped is NOTHING RAN); the queue finished; and the editor exited 0. A non-zero editor exit fails the run even when every test passed (lead's decision: keep it strict, and print the editor's exit code next to the test counts).
  - **Tests that never completed** (since 0.3.5): the engine lists the found tests after `Found N automation tests`, one full name per line (`LogAutomationCommandLine: Display: <tab><name>`, AutomationCommandline.cpp). A found test with no `Test Completed` line is printed as `NotRun <name>` and counted as skipped. The controller skips a test that needs more participants than the run has without any `Test Completed` line, and the queue still ends with exit code 0, so before 0.3.5 such a run read "found 1, 0 skipped". A run that crashed or was stopped before its queue finished counts nothing as skipped: its problem is the unfinished queue.
- **The tree** (0.4.0): `uak build` and `uak test` (editor and cooked) read the version-control state once they hold the lock, on the thread pool alongside the run (`UnrealServices.StartCaptureTree`; after 30 s it is `unknown (not read within 30 s)`, so a slow server never holds the lock up), print it as the summary's first line (`tree: Git <HEAD> + 3 changed (hash <h>): Modified Source/A.cpp, ...`, or with more than 10 changed files only their count and hash; `tree: none (no version control)`), and write it to the result file as `Tree`. The revision is `uak vcs revision`'s, the files `uak vcs changed`'s (Git: modified, added, deleted, renamed, conflicted and untracked, not ignored; Perforce: opened files only, so a writable file that isn't opened counts as unmodified). The hash is the first 12 hex digits of a SHA-256 over each changed file's state, '/'-separated path relative to the root, and content hash, sorted by path, so another edit to the same files gives another hash; past 200 files, and for a file over 16 MiB, the size and write time stand in for the content. It compares trees in one workspace: it hashes the bytes as checked out (CRLF and LF checkouts differ), and not Git's index. The state is the source as the run found it, not proof of what it built or tested: an editor test builds nothing, `-cooked -skipbuild -skipcook` tests a game staged earlier, and an edit made during the run isn't seen. `uak mutate` reads it once, for its tests. A failed query prints `tree: unknown (<why>)` and never fails the run.
- **`-watch=<LogCategory>[,...]`** (0.4.0) counts each category's `Category: Error:` and `Category: Warning:` lines in the run's log (Client.log for a cooked run), after at most two bracketed prefixes, category names ignoring case. The automation framework logs a message a test expects at Verbose, so only real Errors and Warnings count; a watched category with errors prints as an error line, with warnings as a warning. Not judged: the verdict doesn't change.
- **Filter warnings** (0.4.0), against the tests the run found (the `Found N` listing and the completed tests): a `+` part that matched none of them, only when every found test is known; and a part without a trailing `.` (not `StartsWith:`, not anchored at the end) whose matches continue it into more than one name (`Game` matching `Game.*` and `GameBench.*`).
- **`-expect=<file>`** (editor and cooked runs, since 0.3.5; lead's decision, 2026-10-27) names the tests a run must pass: one full test name per line; blank lines and lines starting with `#` are ignored.
  - The run expects the listed names its `-filter` matches, matched as the engine matches it (AutomationCommandline.cpp, and `PassesFilter` in AutomationControllerSettings.h): the filter splits at `+` (empty parts dropped, each part trimmed); `StartsWith:<prefix>` matches the start, with a `.` added when the prefix doesn't end with one; `^<text>` matches the start, `<text>$` the end and `^<text>$` the whole name; anything else matches anywhere; all ignoring case. So one file can list a whole suite, and each run expects its share.
  - `Group:` filters are rejected with `-expect`: their tests come from the project's automation group settings, which uak doesn't read.
  - Since 0.4.0, a test that completed and isn't listed is "unexpected": listed apart, as a warning, and not a failure in itself. A run that passes every other check, and every listed test, but completed unexpected tests exits 3 with `test: PASSED: <L> of <E> listed passed; <U> unexpected (<n> passed, ...); ...`; `-allow-unexpected` makes it 0. A failed unexpected test fails the run as any failed test does, and a missing listed test fails it (exit 1). Before 0.4.0: it passes only when each expected name has a `Test Completed. Result={Success}` line with that `Path=`, and no other test completed. Names compare exactly. The missing tests (with their result, or "did not complete") and the unexpected ones are printed one per line (`missing: <name> (...)`, `unexpected: <name>`), then `expect: N of M expected tests passed, K unexpected`.
  - The file is read before the lock. A missing file, a file with no names, or a filter that matches none of them, is a usage error (exit 2).
- **`uak test -cooked -filter=<filter> [-expect=<file>] [-map=<package>[+<package>...]] [-config=Development] [-platform=host] [-skipbuild] [-skipcook] [-timeout=1800] [-name=uak-test-cooked] [-resultfile=] [-- <game argument>...]`** (since 0.3.5; lead's decision, 2026-10-27: this surface) runs the tests in a cooked game, under the editor lock, through UAT: the engine's `Build/BatchFiles/RunUAT` script for the host (`EngineLayout.RunUatScript`) with `BuildCookRun -project= -platform= -clientconfig= -unattended -nop4 -utf8output -build -cook -stage -pak [-map=] -run -nullrhi -RunAutomationTest=<filter> -RunTimeoutSeconds=<n> [-addcmdline=<game arguments>]`.
  - **Why UAT:** BuildCookRun is the engine's own path from project to running game. It builds the game target, cooks, stages and paks, and its `-RunAutomationTest` starts the game with `-ExecCmds="Automation RunTests <filter>"` and `-testexit="Automation Test Queue Empty"`, then stops it when the queue empties (RunProjectCommand.Automation.cs). The editor-style flags (`-filter`, `-name`, `-resultfile`, `-expect`, `--`) keep their meaning, so a cooked run is the editor run plus `-cooked` and the options that only a cooked run has.
  - **Options:** `-skipbuild` drops `-build` (reuse the game's binaries); `-skipcook` passes `-skipcook -skipstage -pak` (reuse the staged build). `-config=` is Debug, DebugGame, Development or Test: a Shipping game has no automation worker (`WITH_AUTOMATION_WORKER`), so Shipping is a usage error. `-platform=` is the host only (or `host`), because the game runs on this machine. `-map=` takes map package names (letters, digits and `_ - / .`) joined with `+`; the first is the map the game opens. Git Bash turns `-map=/Game/...` into a Windows path before uak sees it, so from Git Bash it needs `MSYS_NO_PATHCONV=1`; the usage error says so when the value holds a `:`. `-timeout=` is `-RunTimeoutSeconds`.
  - `-gpu`, `-windowed`, `-resx=` and `-resy=` are editor options, and `-map=`, `-config=`, `-platform=`, `-skipbuild`, `-skipcook` and `-timeout=` are cooked ones. Giving one to the other kind of run is a usage error.
  - **Logs:** uak sets `uebp_LogFolder` for UAT to `<Project>/Saved/Logs/<name>/` (CommandEnvironment.cs reads it before its defaults). UAT empties that folder first when no other UAT runs, writes its own log there as `Log.txt`, and puts the game's log there as `Client.log` (a source engine's UAT runs the game from a temporary folder and copies `Client.log` back at the end). uak deletes `Client.log` before the run too, so a stale log is never read, and reads it before it releases the lock. UAT's console output goes to `<Project>/Saved/Logs/<name>.log`, outside the folder UAT empties. uak prints both paths first, then UAT's steps (`STAGE COMMAND STARTED`, ...) as they come. `-name` may not be `.` or `..`.
  - **Game arguments after `--`** go to the game through `-addcmdline=`, joined with spaces, always with a space at the end: UAT appends `-testexit=...` straight after the value, so without it the last argument and `-testexit` run together. An argument with white space is quoted with `'`, which UAT turns into `"`.
    - Rejected, written `-Name`, `--Name` or `/Name`, in any case: `-ExecCmds`, `-testexit` and `-abslog` (uak and UAT set them), and `-ReportExportPath` (a cooked game has no HTML report template, so it logs an error).
    - Also rejected: empty arguments, quotes, `% ! & | < > ^` and control characters, because RunUAT.bat strips each argument's quotes and expands it unquoted while it scans its arguments. The same rules hold on every platform. A cooked run's filter is checked the same way (see `-filter`).
  - **The verdict:** a cooked run passes only when all of these hold: UAT exited 0; `Client.log` exists and has `**** TEST COMPLETE. EXIT CODE: 0 ****`; tests were found; none failed (`Result={Fail}`); the found count equals the completed count; at least one passed; UAT didn't stop the game for the timeout (`The run timed out after N seconds`); and the `-expect` check holds, if given. The game's own exit code (`Client exited with error code: N`) is printed but not judged: UAT stops the game once the queue empties, and `Client.log` already gives the tests' result.
  - The result line is `test: <outcome>: P of T passed, F failed, S skipped; found N. UAT exit U, game exit G. <seconds> s. Client log: <path>`. When UAT fails or the game wrote no log, UAT's last 20 lines are printed first. `-resultfile` adds `Mode` (`editor` or `cooked`), `NotRun`, `Expect`, and for a cooked run `Platform`, `Configuration`, `UatExitCode`, `GameExitCode`, `TimedOutAfterSeconds`, `ClientLog` and `UatLog`.
- **`uak test config [-cooked-maps=<a+b>] [-reset]`** (0.4.0) shows or saves the project's own defaults in `<State>/config.json` (the project's state folder; the per-user settings are `<UAK_HOME>/config.json`), written whole, keeping keys uak doesn't know. `uak test -cooked` without `-map=` cooks the saved maps, and says so.
- **`uak mutate -name=<unique> -patch=<diff> -filter=<filter> [editor test options] [-resultfile=] [-MaxParallelActions=]`** (0.4.0) checks that tests catch a change, under one hold of the editor lock. The mutation is in the shared tree for the whole run, so an agent patches only files no other agent is editing, neither edits nor relies on reading them itself until the check ends (even one running detached: an edit made then is made over the mutant), and runs the same tests green first (a verdict means something only against a passing baseline; uak doesn't run one). A check that may run long starts with `uak runs start`, as a killed one leaves its journal. Every agent must run 0.4.0 before the first check: an older `uak` doesn't know the journal; and 0.4.1, whose restore stamps the files for a recompile (below). A commit, shelve or preflight waits until `uak mutate -status` exits 0.
  - **Refusals first** (exit 2, nothing written): a journal left by an earlier run, or one uak can't read; a file it can't copy (held open, say: the copies taken so far are deleted), or a journal folder it can't make; a patch uak can't read (renames, copies, mode changes, binary patches, quoted or non-relative paths, a file twice, a path that resolves to another name, such as a trailing `.` on Windows, or a line after a hunk that is no part of one, such as a hunk line its header doesn't count or an empty line between hunks: so the files and lines it applies are exactly those listed); a created file that exists; a changed or deleted file that is a symbolic link (or junction) or one of several hard links to one file (`MutationJournal.DescribeLink`: writing it whole would replace the link with a file, or part the names, and clearing the read-only flag first clears it for every name; `CanonicalPath.TryGetLinkCount` reads the count, TODO(unix): untested); a patch that doesn't apply as a whole. A changed file may have uncommitted changes: the journal's copy keeps them, byte for byte, so nothing needs committing first. `-cooked` (the staged game would keep the mutation) and `-quiet` are rejected.
  - **Applying:** paths are relative to the workspace root (the Git work tree or Perforce client root), else the project folder. When a file the patch changes or deletes isn't under that root, and the files are all under exactly one Git work tree below the project (a folder holding a `.git` folder or file, at most three folders down, not in `Intermediate`, `Binaries`, `Saved`, `DerivedDataCache`, `Content` or any folder whose name starts with a dot; `MutateCommand.FindNestedGitRoot`, 0.4.1), the paths are taken under that work tree, which applies the patch as a Git workspace does: a `git diff` made in a plugin's own repository, which version control detection (at or above the project) doesn't find. A patch that only adds files, or whose files fit no work tree or several, keeps the root (and is refused where its paths don't resolve). In a Git workspace, `git apply` (after `--numstat` lists the same files, with the same added and removed lines, as uak parsed, and `--check`; a CRLF patch file that doesn't apply is tried again with LF line ends, as git takes a `\r` for content); elsewhere uak's own applier, planned from the journal's copies. Either way each hunk's old lines must match exactly, ignoring only the `\r`s at a line's end, at the line its header names (its old start, moved by the lines the hunks above added or removed), and nowhere else; its new start must name the same place; hunks must be in order, without overlap. There is no search for moved lines: git starts at a hunk's new start and tries the line below before the line above (`find_pos`), a search here would try the other way first, and where the two differ, uak's plan isn't git's bytes, `CheckGitWrite` takes git's write for an edit, and `-accept` merges from the wrong mutant. git tries that line first, but not for every hunk, nor with uak's comparison: a hunk with no context line after its changes is taken for the file's end (`match_end`, as diff writes one only there), applied there whenever its old lines match there too (a zero-context insertion always), else refused; a hunk at line 1 must match at the start (`match_beginning`); and under `core.autocrlf=false` git compares a line's `\r`, so in a file with both line ends its search can land on other lines than uak's comparison does. So uak's applier refuses a hunk without context after its changes unless it ends at the file's end, in both modes, and in a Git workspace the check is `git apply --check -v` (in the C locale), whose `Hunk #<n> succeeded at <line> (offset <k> lines).` (or `Context reduced ...`) names a hunk it would apply elsewhere: any such line refuses the patch (`MutateCommand.GitMovedHunks`). uak's plan is then the lines git changes; only a file that isn't UTF-8 text, which uak's applier can't read, is left unpredicted. uak's applier keeps the file's byte-order mark and every line it doesn't add as it is, its bytes and line end (a hunk's context lines too, and the `\r`s a line holds before its CR LF); an added line gets the line end most of the file's lines have, and an empty file has no line (lines added to it end as the patch says). It refuses a hunk that disagrees with the file about a final line end. Git takes a `\r` for content without `core.autocrlf`, so in a Git workspace a CRLF file under `core.autocrlf=false` needs a patch with CRLF line ends (as `git diff` writes there), though uak's own applier would take an LF one. Just before writing, each file must still hold the bytes it was copied with: for uak's applier, each file just before it is written (`MutationJournal.ThrowIfChangedSinceBegin(MutationFile)`), so a file changed meanwhile is never written, and the files after it neither. Each file is written whole (`MutationJournal.WriteFile`: a temporary file `<file>.<pid>.<guid>.tmp` beside it, flushed, renamed over it, its attributes kept; one a killed write leaves is deleted by the next restore of that file; a link is never written: it throws). A write of its own that fails is put right at once by what the file holds (`PutBackOwnWrite`): exactly its planned bytes (a whole write that failed after its rename, keeping the attributes) are the run's own, saved beside the journal and replaced by the original; its original needs nothing; anything else, the start of the planned bytes too (a whole write never leaves part of itself), is someone else's, never written over, and goes back into the files the restore leaves alone. For git, all of them just before `git apply`, which leaves a window before git reads each file: after `git apply`, each file that holds neither its original bytes nor the planned ones (line ends aside, `CheckGitWrite`) has its bytes saved beside the journal; when uak predicted git's bytes for it, another edit got in, so (git having succeeded) the file is recorded with its planned hash as its mutated one, so no restore takes its bytes for the mutation's, and the check stops with no verdict: the restore leaves it as a conflict (exit 5), for `-accept` to merge the mutation out of it, or refuse it. When git failed because it refused the patch (`GitRefused`, which reads its error output in English by running it with `LC_ALL=C`: every `error:` or `fatal:` line is one git's check of the patch prints, and there is one: `error: patch failed: <file>:<line>`, `error: <file>: patch does not apply`, `error: <file>: No such file or directory` (a file to change is gone) or `error: <file>: already exists in working directory` (a file to create exists); git checks every hunk of every file before it writes one, and a failed write names its file in quotes, so it is never taken for one) and no file holds its planned bytes, git wrote nothing: such a file is an edit that got in before git read it, so it joins the files the restore leaves alone, its bytes aren't saved, and the run is refused (exit 2) with its journal cleared. When git failed otherwise, such a file is a conflict of a run stopped while it wrote the patch (git removes and rewrites files, so it may be git's part write). The files this process never wrote are left alone by the restore (it knows them), and the run is refused (exit 2) once the files it wrote are back. Read-only files (Perforce, not opened) are made writable just before they are written. Each file's +/- lines are printed. A patch after which every file holds its old bytes is refused (exit 2) once the files are put back, without a build.
  - **The journal** (`<State>/Mutations/<name>/`, `MutationJournal` in AgentKit.Locking, so `uak lock run` can read it): before anything is written, each touched file is copied there (as `<n>.<file name>.orig`, so the copies say which file they are even without the record) and recorded with its hash and read-only flag, and so are the folders a created file needs that don't exist yet (phase Applying), each copy and the record flushed to the disk. The journal is written in `<State>/MutationsPending/<name>.<pid>.<guid>/` and renamed into `Mutations/` whole; when it is deleted, it is renamed back out first (retried for 2 s while a reader has a file in it open, `MutationJournal.ClearRetryTime`), so a reader without the lock never sees half of one; it is never deleted in place (a delete stopped part way would leave a journal without its copies): one that still can't be renamed stays whole, in phase Restored, the check's verdict and exit code stand, with a warning that `uak test` refuses until `-restore` clears it (a Restored journal whose copies are gone is still trusted: they are never read again). Setting a journal aside retries the same way; what a killed run leaves in `MutationsPending` holds no patch in the tree, nothing reads it, and `-restore` deletes it. Then the hash of the bytes the patch is to give each file (`PlannedHash`, or `PlannedDeleted`), flushed before anything is written: uak's applier knows them; for `git apply`, uak's applier predicts them from the copies (both read the patch alike, as `--numstat` showed, and apply each hunk at the line its header names), and a file it can't predict (not UTF-8 text) has none. After the whole patch is written, the mutated hashes (Applied); a write that failed or stopped part way leaves the journal in Applying, where only the planned bytes count as the run's. The patch itself is copied there too (`patch.diff`, with its hash), for `-accept`. The files go back from the copies, byte for byte, each copy's hash checked first: only a file that still holds the mutated bytes (or, in Applying, the planned ones) is overwritten (or deleted, or recreated), so an edit made meanwhile is never lost; each file is looked at again just before it is written, after what it held is saved when it is saved (`-force`, `-accept`), and one that changed since it was judged is a conflict, never overwritten; it is written whole (`WriteFile`); a file of a run stopped in Applying that holds neither its original nor its planned bytes may hold part of the patch, and only `-force` puts it back; the folders the patch created are removed when empty; then the phase is Restored, the files are stamped for a recompile (below), the editor target is rebuilt, and the journal is deleted. A Restored journal's files are not checked again (an edit since is someone's work): `-restore` only stamps them (when not stamped yet), rebuilds and clears it. This always runs, after a failed build or test, an exception, or the first Ctrl+C, with no cancellation; a second Ctrl+C or a kill leaves the journal.
    - **The recompile stamp** (0.4.1). UBT counts a direct prerequisite of an action as newer than its output only when it is more than a second newer (`ActionGraph.cs`, in `Actions/` since UE 5.8, in `System/` before, "allow a 1 second slop for network copies"; the output's time is the later of its write and creation times, and a file from the action's dependency list, such as a header or a source in a unity file, counts as soon as it is newer, with no slop), so a file written back within a second of the mutant build's object counted as built: the next build was up to date and the editor kept running the mutant (observed: the mutant `.obj` at 18:55:37.633, the restored source at 18:55:37.859). Once every file of the journals being restored is back, and the mutant build may have run (a run's own restore after its build started, and every `-restore`), `MutateCommand.StampForRecompileAsync` first waits for running `uak compile`s (`UnrealServices.WaitForCompiles`, up to 10 minutes, then a warning: one that read the mutant must write its object before the stamp, or that object would count as newer than it; `uak mutate` and `-restore` refuse outright, each time, while a dead hold's command outlives the lock's wait, `IOrphanedCommandHold`, for the same reason: it may write objects past any stamp). Then it takes the reference (`FindStampReference`): the newest of this machine's clock, the clock of each folder the files are in (`MutationJournal.ProbeFileTime`: a temporary file written there and its time read back, as a file server stamps what a build writes by its own clock), and the later of the write and creation times of the binaries the mutant build wrote (so `Binaries` is recorded before the stamp). It stamps `UnrealServices.RecompileMargin` (2 s) past that, waiting until the newest clock has passed the stamp (2 s, however far ahead a server's clock runs, as it ticks with this one; more only for a binary dated ahead of every clock, and at most `UnrealServices.MaxRecompileWait`, 60 s, past which the time is set all the same, with a warning: a file in the future is recompiled by each build until then, which is slow, not wrong). `MutationJournal.StampForRecompile` sets that time as the write time of each journal file that exists (not those the run never wrote; bytes and attributes, the read-only flag among them, unchanged; where the time can't be set, a share or an ACL, the file's own bytes are written whole, which gives it the clock's time, past the stamp, clearing and putting back its attributes only when the read-only, hidden or system one needs that, as a right that refused the time may refuse them too; and each stamp first deletes a temporary file a killed run's `WriteFile` or probe left beside a file, past where a restore looks), reads it back, and records it (`RecompileStamp`) only when each is more than `UbtTimestampSlop` (1 s) newer than the reference. A journal stamped before that no build showed recompiled is stamped again by `-restore`, a new chance for a rebuild that was up to date. An object file isn't looked at (no list says where each is): on the file system of the file it was built from, it is older than the clock the probe read. UBT then finds each of them, and through its dependency lists every object that includes one, newer than what the mutant build wrote, and recompiles them and relinks, in this rebuild and in any later build; UHT, which compares header times without slop, reruns too. Deleting the mutant's objects was not chosen: which objects hold a patched file (its own, a unity file's, every includer's for a header, a PCH) isn't known reliably, while the time covers them all through UBT's own dependency tracking. A stamp that fails or doesn't take (a file system that dropped the time) leaves the journal Restored and unstamped, with nothing rebuilt: exit 5, and `-restore` stamps again. It assumes the objects are on the file system of the sources, or one whose clock isn't ahead of it. A rebuild that says it succeeded is never taken on trust: see the next item.
    - **A rebuild that fails, or shows nothing** (0.4.1), on another agent's half-edited file, say, no longer fails the check: the files are back byte for byte and stamped, so the verdict stands, and the journal is cleared unless a binary may still hold the mutation. A build's "succeeded" proves nothing by itself: an up-to-date build keeps the mutant's objects and DLLs (the very failure the stamp is there for, should the stamp not have worked). So the journal records what must be seen (`AwaitingRecompile`): the patched sources the mutant build shows a compile of (`FindUncompiled`, as for the verdict, so in a mutant build that failed too), saved before the tests, so a run killed in them leaves it. A file it shows none of isn't in the binaries, and may never compile (not in the target, or a header nothing includes), so no build is asked to: a journal waiting for it could never clear. Before the mutant build the list is null, read as all the patched sources (a journal of 0.4.0); before anything was built it is empty. It stays so after a mutant build that stopped part way (`BuildOutcome.StoppedPartWay`: UBT failed with no `Result:` line and no error it parsed, killed, say), as what such a log shows isn't what it did: an action can finish with no line to show for it. Each build of the journal's target, platform and configuration, given no UBT arguments, after the stamp takes out what it shows (`MutateCommand.ShowsRecompile`, on `BuildOutcome.CompiledClean`): a source by its name or its unity file; a header, which no compile names, or a source the patch deleted, by any compile, as a header shows only in what includes it; a `.swift`, `.proto` or `.rc`, which no compile item is named exactly after (a module's Swift files compile as one action, what compiles from a `.proto` is protoc's `.pb.cc`, and a resource's item is "Resource [x64] Foo.rc"), by any compile too; a file the patch created, which is gone, by any compile or link that succeeded. A compile an error was reported under doesn't count, even an error that repeats another's (`BuildLogSummary.FailedActions`), as it leaves the old object; nor does anything in a build that failed with no error its log names, or in one where a failure can't be laid on the action it ended (`BuildLogSummary.EveryFailureAttributed`): UBT's own "Exited with error code" line, which may reach the log ahead of its action's output and may not name it for sure, or a line under an action with no parsed error that holds a failure word (`error`, `fatal`, `crash`, `abort`, `failed`, `failure`, `segmentation fault`, `access violation`, `out of memory`, `stack dump`; not a `note:`). That only costs evidence in a build that failed, so a stray word errs the safe way: the journal stays for the next build. It reads words, so a failure in other words is missed; the stamp, not this evidence, is what makes a build recompile. The evidence is a second layer, behind the stamp: it catches a stamp that took but that a build didn't act on, and no more. For a source in a unity file it is per module, too: which of a module's `Module.<module>.<n>.cpp` files holds the source isn't in the log, so a compile of any of them counts (a compile of the file's own name likewise, in a project with two files of that name). A build that compiled another unity file of the module, and not the one that holds the source, would pass it. That needs the stamp to have failed in a way its read-back didn't see, and isn't closed here. The evidence adds up over builds: a rebuild that fails on another file counts for what it compiled, and the next build needn't compile that again. Once nothing is awaited and a build succeeds (`HasRecompiled`), the journal is cleared. That never waits for `StillHeldBinaries`: a binary the mutant build wrote may be one an unrelated change made it link, which no later build relinks, and no journal could ever clear. Just before the mutant build, `TargetBinaries` lists the target's binaries: the code files (`.dll`, `.exe`, `.so`, `.dylib`, and any file the receipt lists as an `Executable` or `DynamicLibrary`) in every folder that holds a build product of the editor target's receipt (`<Project>/Binaries/<Platform>/<Target>.target` for Development, else `<Target>-<Platform>-<Configuration>.target`, with `$(EngineDir)` and `$(ProjectDir)` put in), in `<Project>/Binaries/<Platform>`, and in each `Plugins/**/Binaries/<Platform>` (below a folder with a `.uplugin` or `.ubtignore` the walk stops, as UBT's `EnumeratePlugins.cs` does), with each one's write time and length. The list is read again once the build returns (`TargetBinaries.Union`): a build that succeeded rewrote the receipt, and a plugin it linked for the first time has a folder now. Once the files are back, before the stamp, the code files that changed or appeared since are the ones the mutant build wrote (the run held the lock, so nothing else built), checked against the links the build printed (`BuildOutcome.Linked`, `TargetBinaries.FindUnwritten`: Link and its variants, by file name, the `.lib`, `.a`, `.exp` and `.tbd` no process loads aside): a link whose output isn't among them wrote outside the folders (an engine plugin the old receipt doesn't list), or failed, so the list can't be the whole of it and stays unknown. Else it is recorded in the journal (`Binaries`). UBT goes on after an error (`bStopCompilationAfterErrors` is false by default), so a build that failed elsewhere may still have linked the mutant; and a binary written after the stamp was linked from objects recompiled from the files put back. So a journal none of whose recorded binaries may hold the mutation (`StillHeldBinaries`: each is gone, or newer than the stamp; a write time merely changed to one before it, by a copy or a sync, isn't a relink) is spent (`MutationJournal.IsSpent`) and cleared, whatever the rebuild did: the mutant build wrote none, or something relinked them. That needs no compile to be shown: no binary holds the mutant, and the stamp, which is verified, makes the next build recompile the objects that do. Any other stays, Restored and stamped: the check prints `BINARIES PENDING` before its verdict line, with the binaries that may hold the mutation, adds it to `Problems`, sets `BinariesPending` in `-resultfile`, and exits with its verdict (a script reads the field; the exit code stays the verdict's). Which binaries the mutant build wrote is unknown (`Binaries` null, so only a build that shows the compiles clears it) without a receipt uak can read, for a patch that adds or deletes a file or changes a `.Build.cs`, `.Target.cs`, `.uplugin` or `.uproject` (a new module or plugin no receipt lists yet), for a link outside the folders, for a mutant build that stopped part way (no log says what it linked), for a journal of a killed run (no list was taken before its build), and when a folder can't be listed. Records keep `BuildTarget`, `BuildPlatform` and `BuildConfiguration`, the mutant's build.
    - **Who may run while a journal is left.** Every reader that holds the lock (`uak test`, `uak build`, `uak lock run`, `uak mutate` and its `-restore`) treats a journal as its run's own business only when that run is the holder of the hold the reader joined (`MutationJournal.IsRunOf`: the same ID as the holder `holder.json` records for the inherited `UAK_LOCK_HELD` marker, both start times known and matching, and that process surely running). A live run holds the lock, so any other journal is a stopped run's; an unknown start time never matches, so a protected process that reuses a killed run's ID never hides its journal. `uak test`, `uak lock run` and `uak mutate` refuse (exit 2) while one is left; `uak build` while it is not Restored. Since 0.4.1, a spent journal (`IsSpent`) is cleared by the reader instead, under the lock, and allowed; and a `uak build` given no UBT arguments (which could build part of the target) notes, still under its lock, what it compiled in every stamped Restored journal whose mutant was built as its target, platform and configuration, and, when it succeeds, clears each that has seen everything recompiled (`MutationJournal.ClearAfterBuild`): those compiles took the mutant's objects out, and that build relinked them. One it can't clear stays, with a warning that says so. An unstamped Restored journal (of 0.4.0, or one whose stamp didn't take) waits for `-restore`, which stamps first and records the build a journal of 0.4.0 doesn't name. A folder under `Mutations/` whose `journal.json` is missing (with copies left), empty, truncated, of an unknown phase, or names copies that are gone (unless Restored), is refused the same way, never skipped. A folder with neither (a run killed before it copied anything) is deleted by the next `Begin` of its name, and refused (exit 2) when it can't be. `uak vcs shelve` and `uak horde preflight -shelve` look at the found project's state folder only: with no project found, they warn that they can't look (`MutationFolders.DescribeUnchecked`; there is no list of projects to search).
    - **`uak mutate -restore [-name=] [-accept | -force]`** finishes the job, run on its own (inside `uak lock run` it is refused like any other reader: the messages say so). It clears a journal as the check does (a rebuild that shows the compiles, or no binary that may hold the mutation), else exits 5, except that `-force` sets aside a journal whose rebuild succeeded without showing them, with a warning: the way out for a file no build of this target compiles. A folder uak can't read is cleared only by `-accept`: it stamps the files the record can still name (`MutationFolders.ReadListedFiles`), and refuses a rebuild that compiled nothing, as an `.orig` copied back by hand keeps the old write time of its copy, so its own message tells the user to give such a file a new one; only a whole list of the folder's own run that names no source passes with nothing compiled (`MutationFolders.ReadWholeList`), as a partial list or one that names another run leaves the sources unknown. Refused (exit 2, nothing changed), each time, while the killed check's command outlives the lock's wait for it (`IOrphanedCommandHold`), until that process has gone or `uak lock forget-orphan` drops its record; a new check is refused the same way. A file changed since the patch is left and reported (exit 5); an edit made while the check ran is made over the mutant, so it may keep the mutation. A file that became a link since (another hard link to it, or a symbolic link in its place) is left too, in every mode, as uak never writes a link (`MutationRestore.BecameLink`), and the hint says so: remove the other link, then run `-restore` again. Then, with `-name=`, `-accept` merges such a file three ways (`MutationUndo`, from the journal's copy of the patch; `ThreeWayMerge`, a diff3 in C#, so it never depends on git), and takes the mutation out only where it is pinned (the anchor rule, below) and the edit left the lines around it alone (the strict near-edit rule, below): anything else it refuses, and `-force` (which saves the edit) is the way on. The base is the mutant (the patch applied to the journal's copy of the original with uak's applier, each hunk at the line its header names), "ours" the file as it is, "theirs" the original. "Theirs" is matched with the mutant line for line except where the patch changed it (`MutationUndo.FindChanges`: each run of `-` and `+` lines of a hunk, narrowed to the lines that differ), not by an edit script, which may pick another of several like lines. "Ours" is a shortest edit script (Myers, after the lines both share at their start; a side that both removes and adds lines, more than 2,000 of them between its first and last change, is refused), found twice: keeping lines as early as it can, and, on both sides' lines reversed, as late (each also setting aside the lines both share at their end only when the search can't do without: that would keep them as late as it can, so a function added after the mutated one, both ending in `}`, would be read as lines added inside it). Lines compare by their bytes without the line end's kind, but with whether one follows, and a byte-order mark is no part of them. Changes with an unchanged base line between them merge; changes to the same or adjacent lines conflict, unless both sides hold the same lines there (merged as one change, and listed). The file gets the edit with the mutated lines as they were (what it held saved as a `.current` first; lines from the original take the file's line end when it uses one kind; the file's byte-order mark and attributes are kept) only when: one of the two merges is clean (the early one's result, else the late one's); it lists no place both sides changed alike (the mutation taken out by hand, or the original's lines written next to it: uak can't tell the edit's change from the undo's); each change is pinned (`MutationUndo.FindAnchor`, `PlaceAnchors`): its mutated lines (for a change that only removed lines, the place they were) with the mutant's line before and after them (the file's start or end where there is none), grown upward until the block occurs once in the mutant and, on its own, downward until it does, must be in the file once, intact (line ends' kind aside), and the merge's alignment must keep each line of that block as the line it is there (the edit changed none of them, nor put a line among them), the merge being exactly the file with each change's mutated lines, there, replaced by the original's (the smallest block that occurs once is not enough: of two functions alike but for their signatures, the block below the mutated line, grown one way, is the other function's once an edit swaps the two, and the merge reads the swap as the two signatures swapped, a shorter edit, and takes the mutation out of the wrong function); the strict near-edit rule holds, checked before the rest of the anchor rule (`MutationUndo.FindNearEdit`): the edit changed, copied, moved or deleted no line of each change's anchor or of its neighbours (the line before and after the anchor, or the file's start or end where the anchor reaches one), judged by comparing the mutant and the file around the anchor, so the anchor with its neighbours is in the file exactly once, byte for byte as in the mutant, a line end's `\r` aside only where the file's line ends allow it (`SameLines`: on the lines the patch added, whose line end's kind git's or uak's applier chose, so the mutant made again may differ there, and everywhere in a file that has one kind of line end, which tells no lines apart by it), and nowhere else even with the `\r`s aside, both alignments keep each of its lines as the line it is there, none of its lines (the mutated ones among them) is in the file more often than in the mutant (a copy; `IsTrivial` leaves out a line of punctuation alone, such as `};` or `);`, which many edits write, but not a blank line or a brace alone: with all three left out review 6's fuzzer finds a kept mutation on 2 of 4 seeds and its positional metric 16 wrong results where there was 1, and with only one of them back neither is cured), and no line the change pins (a mutated line, or the line before and after lines it only removed) is like another of its lines (`FindLikeLine`: a brace next to a brace, a blank line next to a blank line), which an edit could swap it with without changing a byte; its refusal names the lines the edit touched (the mutant's line numbers: changed, moved or deleted, lines put between, lines put before or after at the file's start or end, lines copied) and offers `-force`, which puts the original back and saves the edit; the rule only adds refusals, so what it lets through still goes through the other checks; for each place the patch changed, its mutated lines with the mutant's line before and after them (one each, where there is one) are in the result no more often than in the original, and so is each non-blank mutated line on its own, white space aside, a line of code counting in every line that starts with it (an edit that copied the mutated code, or wrote it anew, can draw the alignment to the copy, so the merge takes the copy out and leaves the mutation where it was, maybe edited in place; an edit that adds such code of its own is refused too); and the other merge gives the same bytes, changes that only touch put in order, as their order is plain, and its alignment keeps every line of each block and puts each change's mutated lines (or the two lines around a removal) where the merge's does (`FindGuessedAnchor`; it may read lines the edit added as put between the mutated lines and the block's others, as for a function added after the mutated one, both ending in `}`): where the two disagree, the result rests on which of several like lines is the edit's, a guess. A file whose merge equals it as it is (the patch changes none of its lines) is kept. Anything else refuses the file, saying why: a conflict names its lines as they are now and what the original has there. So an edit that moves the mutated lines away from what pins them, swaps the mutated function with one alike, changes, copies or removes a line of the block or the line next to it, or leaves the block in the file twice, is refused, and so is an edit of the mutated function's signature, or a function added anywhere when the anchor holds a brace (it copies it): the merge is kept for edits elsewhere, and the cost is in refusals, -force being the way out (on review 6's fuzzer, -accept keeps about 4.5% of edited files where it kept about 18%; on review 5's, edits far from the mutation are refused 79% of the time where they were 28%). What no comparison of bytes can tell is left: an edit that removes lines around the mutation and writes the very same bytes back where they were, so that the file reads, around each anchor, as the mutant did, reads as one that left them alone, and the mutation is taken out of where they now are, the right result for that reading. Review 6's fuzzer, which judges by which line is which, finds no mutation kept and no removed lines put back between the wrong two in 4 seeds of 200,000 cases; it still finds about 10 to 40 cases per 200,000 (seeds 1 to 8) where the edit removed a line around the mutation and wrote the same bytes back, which a shorter reading of the file calls untouched (and for that reading the result is right), nearly all in files of a few distinct lines. A file the patch created or deleted is never kept once edited, one deleted since is kept (it holds no mutation), and one uak can't check is refused. For a refused file, `-force` puts the original back and saves the edit beside the journal, to be made again on the original: there is no loop of fixing by hand and accepting again. A file that still holds the mutation is put back, and `-accept` also clears a journal uak can't read, once its files are checked by hand. Or `-force` puts the originals back over every file, saving the bytes it overwrites as `<n>.<UTC time>.current`, never over bytes saved before. A run stopped while it wrote the patch is never accepted: the hint offers `-force` alone. Both rebuild, then move the journal with its copies to `<State>/DiscardedMutations/<name>-<UTC time>/` and print where. A journal that can't be cleared (a reader holds a file in it) makes `-restore` exit 5: the files are back and rebuilt, and running it again clears it. A rebuild that fails clears a spent journal (exit 0, with a warning) and leaves any other, stamped (exit 5: tests wait for a build that succeeds; builds, compiles and shelves don't). The restore waits for an orphaned build of the killed run as any lock holder does (up to 30 s); TODO(unix): without PDEATHSIG an orphaned UBT can outlive that on Linux and Mac, and `-restore` then refuses, as above.
    - **`uak mutate -status`** lists the journals left, running (the process surely runs) or stopped, with their phase and files, without the lock (a running check holds it): exit 0 when none is, 5 when one is or a folder can't be read (looked at again for up to a second first). Since 0.4.1 a Restored journal is listed as a warning (its files are back; tests wait for its binaries) and doesn't make it exit 5: a commit, shelve or preflight of source files ships none of its patch, and `vcs shelve` and `horde preflight -shelve` refuse a binary that may hold it (a commit of binaries is the lead's to leave out).
  - **Verdict:** only a test result is one. 0 caught (the mutant built, the tests ran, and a test, or a listed test, completed with `Result={Fail}`: a skipped listed test, or a state such as NotRun, is no failure); 6 survived (the tests passed, with or without unexpected tests); 3 the mutant didn't build (an error in a patched file, a relative path matching the patched file's last path parts, or in a file whose `#include` names a patched header, its last path part compared whole: `BarFoo.h` is not `Foo.h`; an error reached only through another header, or a linker error, blames nothing); 4 inconclusive: the build shows no compile of a patched source file, neither by its name (adaptive unity compiles an edited file on its own) nor of its module's unity file (`Module.<module>.cpp` or `Module.<module>.<n>.cpp`, not the generated `.gen.` ones; the module is the nearest folder above with a `*.Build.cs`, and its unity files are named after the `ShortName` that `Build.cs` sets, if any, as UEBuildModuleCPP's `Rules.ShortName ?? Name` does; an action's item leaves out UE 5.8 UBT's `[Cache]`, `[NoUba]` and `[RemoteExecutor: host]` tags and its optional target and times), or no compile at all for a patched header or deleted source file (so the binaries may not hold the patch), or failed with no error in a patched file (another agent's broken file, a locked DLL), or the tests didn't start, ran nothing, or ended without a failed test but not cleanly (a crash, the editor's exit code, a listed test that was skipped or never completed); 5 restore failed (a file changed since the patch, or the files are back but couldn't be stamped for a recompile: each said apart; before 0.4.1, a rebuild after that failed was one too, and now leaves the verdict standing); 1 no verdict (uak failed or was cancelled, after putting the files back); 2 refused. Survived is not 1, which a killed process and every uak failure exit with. A compile matched by the patched file's name alone, while the project's `Source` or `Plugins` has another file of that name (outside build output), is warned about (and listed in `Problems`): UBT names a file it compiles on its own by its name alone, so it may be the other's. `-resultfile` is the check's own (`Verdict`, `ExitCode`, `BinariesPending`, `Files` with their +/- lines, `Tests`, `Problems`, `Message`): deleted first, written at every exit; the inner test writes none. `uak build`, `uak test` and `uak compile` delete their `-resultfile` as they start too, and write `{ Command, Outcome: "refused" | "stopped", ExitCode, Message }` when refused or stopped before their own (`UnrealServices.WithFreshResultFileAsync`).
- **Logs:** compile and build write UBT's output to `<State>/Logs/<command>-<UTC time>-<pid>.log`. UBT and Build-script output is decoded with `ProcessRunner.ConsoleEncoding` (the OEM code page on Windows).
  - Both print `Log: <path>` first, and flush the log line by line, so a long run can be followed while it goes.
  - Both echo UBT's latest `[n/N]` action line, with the time so far, at most once a minute (`UbtProgress`, on `UnrealServices.Clock`), so a long build is visibly alive. A run shorter than a minute echoes nothing.
- **`-filter`** rejects `,` `;` `|` quotes, backticks and white space, which would break the `-ExecCmds` list. A cooked run's filter also rejects `% ! & < >`, and `^` except at the start of a `+` part (the engine's "match from the start"), because it passes through RunUAT.bat like the game arguments.
- **Headers under `-dependents`:** the header counts as compiled only through its own `<Name>.h.cpp` (or `.h.obj`) action. The other compiled units are reported on their own lines and never stand in for it.
- **Other rules:**
  - Paths to UBT, the editor and scripts come from the engine directory and the host platform. Never hard-code `.exe` or `Win64`; use a helper in Core.
  - Parallelism is capped by `-MaxParallelActions` when given, else by `UAK_MAX_PARALLEL_ACTIONS`.

## Plugin content

- **Agents** (named `unreal-agent-kit:<name>` in Claude Code; before 0.3.0 they were `ue-<name>`, see CHANGELOG.md):
  - `low`, running on Sonnet;
  - `medium` and `high`, on the lead's model, and `xhigh`, on Opus;
  - `runner`, on Sonnet at low effort, which cannot edit: it runs a given list and reports, so a verification never changes what it verifies;
  - `research`, read-only, on Opus at high effort (the lead raises it to extra-high for an engine fact the design depends on), for engine investigations answered with `file:line` evidence. Its reading never conflicts with workers' edits, but its experiments queue like any run: `uak test` takes the editor lock, and `uak compile` waits for UBT's mutex. `uak compile` only compiles files inside a module, so an experiment compiles existing project files only; one that needs new code asks the lead, and a worker writes it (a file a researcher added to a module would be picked up by other agents' builds);
  - `review`, read-only, on Opus at extra-high effort;
  - `review-diff`, read-only, on the lead's model at high effort, for scoped re-reviews: given a fix diff (or commit range) and the findings it fixes, it checks that each is fixed and hunts for new issues the diff introduced, without reviewing the rest of the project, and says what it didn't check. It is not pinned to Opus: it judges named findings against a small diff, and the review loop runs it once per round of fixes;
  - `architect`, on Opus at extra-high effort, which drafts a milestone's plan, briefs README and epic briefs from the skill's templates, writing only the draft files the lead names; it has no shell (`Bash` and `PowerShell` are disallowed), so it runs nothing, and it never edits code;
  - Opus is pinned for `xhigh`, `research`, `review` and `architect`, whose output the others act on without re-checking, so a lead on a cheaper model doesn't lower them; `medium`, `high` and `review-diff` inherit the lead's model. The Opus agents are the expensive ones, so the workflow skill keeps them to the work that needs them (below).
- **Their ground rules:**
  - never spawn agents (`disallowedTools: Agent`);
  - never kill processes or commit unless told;
  - take the lock for editor and build runs;
  - start anything that may run over an hour detached through `uak runs start`, and wait for it with one background `uak runs wait`;
  - ask the lead with SendMessage to "main";
  - ask for a runner for long, low-judgment work;
  - follow epic briefs, and rewrite their Current state and Next step at every hand-back, so the lead can respawn a fresh agent from the brief instead of resuming a large context;
  - read large files in parts (Grep, then line ranges), and after a compaction re-read only what the next action needs, so the context doesn't fill again at once (since 0.3.6, after an agent looped for hours re-reading a long brief and large sources after each compaction);
  - no new batch or shell scripts: tools go in `uak`.
- **The workflow skill:** briefs (a README plus E#.md per milestone), caps, effort tiers and their cost (`xhigh` only for formats, contracts and correctness-critical algorithms, with fix passes at `high`; `research` at extra-high only for an engine fact the design rests on; `review` for first reviews and `review-diff` for re-reviews of fixes), delegation (runner and research requests), when to resume an agent and when to respawn it from its brief (after a usage limit or a restart, respawning usually costs less), how to spot and stop an agent stuck in a compaction loop (several compactions with no file change, build or test between them; frequent compactions alone are not one), reviews (review, fix, re-review until no critical or major finding is left), spec-doc sync, restarting the lead at milestone boundaries (a handoff in its memory and the project's files, then `/clear`), and an opt-in usage-limit watchdog (only if the project's owner allows auto-resume).

  - a CLAUDE.md snippet;
  - how to build `uak` on first use.
- **SessionStart hook** (`hooks/hooks.json`, `hooks/check-uak.sh`): at startup, only in an Unreal project (a `.uproject` at or above the project folder, or an engine root), it checks for `$UAK_HOME/<plugin version>/uak`. When that is missing it shows the user a one-line notice, and tells Claude to ask them with AskUserQuestion, before acting on their first message, whether to publish now. A hook can't start a turn itself, so this is the earliest the question can come. A plugin update therefore prompts a republish. It only reads files, always exits 0, and is POSIX `sh`, because it must run on every user's machine before `uak` exists (Claude Code runs hooks in Git Bash on Windows, so it needs Git for Windows there; the docs say so). Publishing from the installed plugin copy is fine: only its throwaway `tools/bin` and `tools/obj` are written there, and the install goes to `$UAK_HOME`.
  - The walk up for a `.uproject` stops before the filesystem root and after 40 levels, and never searches a UNC host: in Git Bash, `/` globs as `//*`, which browses the network for seconds.
  - On Windows, paths are converted to POSIX form with `cygpath -u` when it exists, and the default `UAK_HOME` is under `USERPROFILE`, as `uak` itself finds it, not Git Bash's `HOME`.
  - **The command.** It finds the project's engine as `uak` does, as far as `sh` can: `UAK_ENGINE`; else the `.uproject`'s `EngineAssociation` (a path, relative to the project; empty, the engine containing the project; a version, the launcher's default install folder on Windows and Mac). It then takes that engine's newest bundled SDK for this host, so the command it gives is exact. A registered build's GUID needs the registry, so then it gives the generic command and Claude finds the engine.
  - **Old versions.** When older version folders are installed, the question offers to remove them after a successful publish, folder by folder (`rm -rf` on each listed version, never `State/`). A folder a detached run still holds open fails to delete and is left.
  - **Bash, not PowerShell.** The commands it gives are `sh` (a `VAR=value` prefix, `/c/`-style paths on Windows), so it tells Claude to run them with its Bash tool, never PowerShell or cmd.
  - A test runs it through `sh` (`HookTests`): the one on PATH, else, on Windows, Git for Windows' `bin/sh.exe` beside `git.exe` (PowerShell and cmd usually have only Git's `cmd` folder on PATH), so the hook tests run there too.
- **`uak` on PATH** (`bin/uak`, `bin/uak.cmd`): Claude Code puts an enabled plugin's `bin/` folder on the PATH of the shell it runs commands in, after the user's own entries. Each shim runs `$UAK_HOME/<plugin version>/uak` with its arguments as given, and exits with its exit code. The version comes from the plugin's own `plugin.json`, and the home is found as the hook finds it (`USERPROFILE` on Windows). So a plugin update moves every session to the new version's `uak`, with no PATH change. With no published `uak`, a shim prints one line that points to docs/INSTALL.md and exits 2, uak's setup-error code.
  - `bin/uak` is POSIX `sh`, for Git Bash, Linux and Mac; git keeps its executable bit. `bin/uak.cmd` is for PowerShell and cmd, which find it through PATHEXT and skip the extensionless file. `uak lock run` and `uak runs start` find `uak.cmd` the same way.
  - `uak.cmd` passes `%*` on through cmd, which may change `%`, `^` and `!` outside quotes. For such arguments, call `uak.exe` by its full path.
  - A `uak` the user put on PATH comes first, so after an update it must point at the new version's folder, or go.
  - The Claude Code docs promise `bin/` for the Bash tool. claude.ai and Cowork don't install a plugin with a top-level `bin/`.
  - `HookTests` runs both shims against a stand-in published `uak`: the test child's launcher, which the test project's build copies to `FakeUak/0.0.0-shim/uak[.exe]`.

## Shared contracts

- `IUakCommand` and `UakContext` (in Core) are what every other library, and every project command (see "Installing `uak`"), builds against.
- Keep changes to them additive. Project commands are built separately from the kit, so a breaking change would break them silently.
